# 🟢 Part 1: Fresher (0–1 year)

### Q1. What is NLP? *(Must-know)*
Natural Language Processing is the field of enabling computers to **understand, analyse and generate human language**. It spans text classification, translation, summarisation, question answering, search, chatbots and speech-text pipelines.

### Q2. Why is NLP hard?
Ambiguity ("bank" = river or money), context dependence, sarcasm, idioms, spelling noise, morphology, code-mixing (Hinglish), long-range dependencies, low-resource languages, and the need for world knowledge.

### Q3. Common NLP tasks
| Level | Tasks |
|---|---|
| Token level | POS tagging, NER, chunking |
| Sentence/document level | Classification, sentiment, similarity, topic modelling |
| Sequence-to-sequence | Translation, summarisation, paraphrasing |
| Retrieval/QA | Search, extractive/generative QA, RAG |
| Generation | Chatbots, code, story, data-to-text |

### Q4. What is text preprocessing? *(Must-know)*
Cleaning raw text before modelling: lowercasing, removing HTML/URLs/emojis (or converting), handling punctuation and numbers, normalising Unicode, tokenisation, stop-word removal, stemming/lemmatisation. **Modern Transformer pipelines need much less** (keep case, punctuation and stop words; use the model's own tokenizer).

### Q5. Tokenisation
Splitting text into units (words, subwords, characters). Word tokenisers fail on contractions and compound words; subword tokenisers (BPE, WordPiece, SentencePiece) handle rare words by splitting them into pieces.
```python
import spacy
nlp = spacy.load("en_core_web_sm")
[t.text for t in nlp("Ritesh Kumar doesn't like spam.")]
```

### Q6. Stop words
Very common words ("the", "is", "of") often removed for bag-of-words models. Don't remove them for tasks where they matter (negation "not", question answering, Transformers).

### Q7. Stemming vs lemmatisation *(Must-know)*
| | Stemming | Lemmatisation |
|---|---|---|
| Method | Chop suffixes by rules (Porter, Snowball) | Dictionary + POS-based base form |
| Output | May not be a word ("studi") | Valid word ("study") |
| Speed | Fast | Slower, more accurate |
| Example | "running" → "run" | "better" → "good" |

### Q8. Bag of Words (BoW)
Represents a document as word counts, ignoring order. Simple, sparse, high-dimensional; loses context and word order.
```python
from sklearn.feature_extraction.text import CountVectorizer
X = CountVectorizer().fit_transform(["I love NLP", "NLP loves me"])
```

### Q9. TF-IDF *(Must-know)*
Weights words by importance: `tfidf(t,d) = tf(t,d) × log(N / df(t))` (sklearn uses a smoothed variant). Frequent in a document but rare across documents → high score. Common words get low weight.
```python
from sklearn.feature_extraction.text import TfidfVectorizer
vec = TfidfVectorizer(ngram_range=(1, 2), min_df=2, sublinear_tf=True)
```

### Q10. n-grams
Contiguous sequences of `n` tokens (bigrams, trigrams). They capture local order ("not good") but increase feature-space size quickly.

### Q11. Sparse vs dense representations
BoW/TF-IDF are sparse, high-dimensional, with no semantic similarity ("car" ≠ "automobile"). Embeddings are dense, low-dimensional (100–1536) vectors where similar meanings are close.

### Q12. Text classification pipeline
Clean → vectorise (TF-IDF) → classifier (Logistic Regression / Linear SVM / Naive Bayes) → evaluate (F1, confusion matrix). This is a strong, fast baseline before moving to Transformers.
```python
from sklearn.pipeline import make_pipeline
from sklearn.linear_model import LogisticRegression
clf = make_pipeline(TfidfVectorizer(), LogisticRegression(max_iter=1000)).fit(X_tr, y_tr)
```

### Q13. Naive Bayes for text
Applies Bayes' rule with word-independence assumption; multinomial NB works on counts/TF-IDF. Very fast, good for small data; use Laplace smoothing to handle unseen words.

### Q14. Cosine similarity
`cos(a, b) = a·b / (‖a‖‖b‖)`, the angle between vectors, ignoring length. The standard measure for comparing TF-IDF or embedding vectors.

### Q15. Word embeddings (intro) *(Must-know)*
Dense vectors learned so that words used in similar contexts are close. "king − man + woman ≈ queen" is the classic illustration. Word2Vec, GloVe and FastText are static embeddings (one vector per word).

### Q16. Word2Vec: CBOW vs Skip-gram
- **CBOW**: predict the target word from surrounding context; faster.
- **Skip-gram**: predict context words from the target; better for rare words.
Uses negative sampling or hierarchical softmax for efficiency.

### Q17. Named Entity Recognition (NER)
Identify and classify entities (PERSON, ORG, LOC, DATE, MONEY). Usually sequence labelling with BIO tags: `B-PER I-PER O`.
```python
doc = nlp("Ritesh Kumar joined Infosys in Pune.")
[(e.text, e.label_) for e in doc.ents]
```

### Q18. Part-of-speech (POS) tagging
Assigning grammatical tags (NOUN, VERB, ADJ). Useful for lemmatisation, parsing and rule-based extraction.

### Q19. Sentiment analysis
Classifying opinion polarity (positive/negative/neutral) or emotion/aspect. Approaches: lexicon (VADER), classic ML, fine-tuned Transformers, or LLM prompting. Challenges: sarcasm, negation, domain shift.

### Q20. Language model (LM) basics *(Must-know)*
A model that assigns probabilities to token sequences: `P(w1…wn) = ΠP(wi | w<i)`. n-gram LMs use counts with smoothing; neural LMs (RNN, Transformer) predict the next token. Modern LLMs are huge Transformer LMs.

### Q21. Perplexity
`PPL = exp(cross-entropy)`; the effective branching factor. Lower is better; comparable only with the same tokenizer and dataset.

### Q22. RNN, LSTM and GRU for text
RNNs process tokens sequentially; LSTM/GRU use gates to keep long-term information and reduce vanishing gradients. Largely superseded by Transformers but still used in small/streaming settings.

### Q23. Attention and Transformers (intro) *(Must-know)*
Attention lets each token weigh all other tokens: `softmax(QKᵀ/√d)V`. The Transformer stacks self-attention and feed-forward layers, trains in parallel and captures long-range context. BERT, GPT, T5 and all modern LLMs are Transformers.

### Q24. BERT in one paragraph
A bidirectional **encoder** pre-trained with **masked language modelling** (predict masked tokens) on large text, then fine-tuned for classification, NER, QA. Input is `[CLS] sentence [SEP]`; `[CLS]` embedding often feeds a classifier.

### Q25. GPT in one paragraph
A **decoder-only** causal Transformer trained to predict the next token. Generates text autoregressively; scaled up and instruction-tuned, it becomes a chat/LLM.

### Q26. Pre-training vs fine-tuning
Pre-training learns general language knowledge from huge unlabelled text. Fine-tuning adapts the model to a specific task/domain with labelled data, usually at a small learning rate.

### Q27. Using a pre-trained model in 3 lines
```python
from transformers import pipeline
clf = pipeline("sentiment-analysis")
clf("The delivery was late but support was helpful.")
```

### Q28. Handling out-of-vocabulary (OOV) words
Subword tokenisation (BPE/WordPiece), character n-grams (FastText), byte-level BPE (GPT), and `<UNK>` tokens in older models.

### Q29. Evaluation metrics: classification vs generation
Classification: accuracy, precision, recall, F1. Generation: BLEU, ROUGE, METEOR, BERTScore, perplexity, human evaluation. Retrieval: Recall@k, MRR, nDCG.

### Q30. Data splits and leakage in NLP
Split by document/user/time, not by sentence, to avoid near-duplicates across train and test. Deduplicate before splitting; fit TF-IDF only on training data.

# 🔵 Part 2: Junior (1–3 years)

### Q31. Subword tokenisation: BPE vs WordPiece vs Unigram *(Must-know)*
- **BPE**: start with characters/bytes, repeatedly merge the most frequent pair (GPT, Llama).
- **WordPiece**: merges chosen to maximise likelihood; `##` continuation pieces (BERT).
- **Unigram (SentencePiece)**: start big, prune tokens by likelihood; language-agnostic, no pre-tokenisation.
Tokenizer and model must match; vocabulary size trades sequence length vs embedding size.

### Q32. TF-IDF vs embeddings for search
TF-IDF/BM25: exact keyword matching, interpretable, fast, great for rare terms and IDs. Embeddings: semantic matching ("refund" ≈ "money back"), weaker on exact tokens. **Hybrid search** (BM25 + dense, fused with reciprocal rank fusion) is a strong default.

### Q33. BM25
A probabilistic ranking function improving TF-IDF with term-frequency saturation (`k1`) and document-length normalisation (`b`). The standard lexical retrieval baseline (Elasticsearch/Lucene default).

### Q34. GloVe vs Word2Vec vs FastText
- Word2Vec: local context window prediction.
- GloVe: factorises global co-occurrence statistics.
- FastText: word = sum of character n-gram vectors → handles OOV and morphology (good for Indic/agglutinative languages).

### Q35. Static vs contextual embeddings *(Must-know)*
Static: one vector per word regardless of context. Contextual (ELMo, BERT, GPT): the vector depends on the sentence ("bank" differs in "river bank" and "bank loan"), solving polysemy.

### Q36. Fine-tuning BERT for classification
```python
from transformers import AutoTokenizer, AutoModelForSequenceClassification, TrainingArguments, Trainer
name = "bert-base-uncased"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForSequenceClassification.from_pretrained(name, num_labels=3)
enc = lambda b: tok(b["text"], truncation=True, max_length=256)
args = TrainingArguments("out", learning_rate=2e-5, per_device_train_batch_size=16,
                         num_train_epochs=3, weight_decay=0.01, eval_strategy="epoch")
Trainer(model=model, args=args, train_dataset=train_ds.map(enc, batched=True),
        eval_dataset=val_ds.map(enc, batched=True), tokenizer=tok).train()
```
Typical LR 2e-5 – 5e-5, 2–4 epochs, warm-up, dynamic padding.

### Q37. Truncation, padding and max length
Models have a context limit (512 for BERT). Truncate or chunk long documents (sliding window with overlap) and aggregate predictions. Use dynamic padding (`DataCollatorWithPadding`) to save compute.

### Q38. Attention masks and special tokens
`attention_mask` marks real tokens (1) vs padding (0). Special tokens: `[CLS]`, `[SEP]`, `[PAD]`, `[MASK]` (BERT); `<s>`, `</s>`, `<pad>` (others). `token_type_ids` separate sentence pairs.

### Q39. NER with Transformers
Token classification with BIO labels; the problem is **subword alignment**: label the first subword (or all) and set others to `-100` to ignore in loss. Evaluate entity-level F1 with `seqeval`, not token accuracy.

### Q40. Sentence similarity and embeddings *(Must-know)*
Sentence-BERT style bi-encoders produce a fixed vector per sentence, trained with contrastive/siamese objectives.
```python
from sentence_transformers import SentenceTransformer, util
m = SentenceTransformer("all-MiniLM-L6-v2")
e = m.encode(["refund policy", "how to get my money back"], normalize_embeddings=True)
util.cos_sim(e[0], e[1])
```

### Q41. Bi-encoder vs cross-encoder
Bi-encoder: encode query and document separately, fast, precomputable, used for retrieval. Cross-encoder: encode the pair jointly, more accurate but slow, used for **re-ranking** the top-k candidates.

### Q42. Topic modelling
LDA (probabilistic, bag-of-words), NMF, and embedding-based BERTopic (embeddings → UMAP → HDBSCAN → c-TF-IDF). Evaluate with coherence (C_v) and human inspection.

### Q43. Text clustering
Embed documents, reduce dimension (UMAP/PCA), cluster (K-Means/HDBSCAN), label clusters with top TF-IDF terms or an LLM summary.

### Q44. Dependency parsing vs constituency parsing
Dependency: head-dependent word relations (subject, object). Constituency: nested phrase structure (NP, VP). Dependencies are widely used for information extraction.

### Q45. Coreference resolution
Linking mentions that refer to the same entity ("Ritesh … he … the engineer"). Important for summarisation and QA; hard and often handled implicitly by LLMs.

### Q46. Relation and information extraction
Extract triples (subject, relation, object) using rules (patterns, dependency paths), supervised models, or prompting LLMs for structured JSON output. Validate output schema and normalise entities.

### Q47. Sequence labelling with CRF
Conditional Random Fields model label dependencies (e.g., `I-PER` cannot follow `O`). BiLSTM-CRF was state-of-the-art before Transformers; CRF layers still help constrain outputs.

### Q48. Seq2seq with attention
Encoder compresses the input; decoder generates output step by step; attention lets the decoder look at all encoder states, fixing the fixed-vector bottleneck. Transformers generalise this idea.

### Q49. Decoding strategies *(Must-know)*
| Method | Behaviour |
|---|---|
| Greedy | Pick the argmax each step; repetitive |
| Beam search | Keep top-`k` sequences; good for translation/summarisation |
| Temperature | Scales logits; low = deterministic, high = random |
| Top-k | Sample from the `k` most likely tokens |
| Top-p (nucleus) | Sample from the smallest set with cumulative prob ≥ p |
| Repetition penalty / no-repeat n-gram | Reduces loops |

### Q50. BLEU and ROUGE *(Must-know)*
BLEU: n-gram **precision** with brevity penalty (translation). ROUGE: n-gram **recall** (ROUGE-N) or longest common subsequence (ROUGE-L) for summarisation. Both ignore meaning; BERTScore/COMET and human evaluation are better for semantics.

### Q51. Extractive vs abstractive summarisation
Extractive selects existing sentences (TextRank, BERT-based); abstractive generates new text (BART, T5, LLMs) but can **hallucinate**. Evaluate faithfulness, not only ROUGE.

### Q52. Question answering types
Extractive (span from context, SQuAD), generative (answer text), open-domain (retrieve + read), multi-hop, conversational. Metrics: Exact Match and F1 for spans.

### Q53. Handling imbalanced text classes
Class weights, resampling on training only, focal loss, threshold tuning, data augmentation (back-translation, synonym replacement, LLM paraphrases), and macro-F1 evaluation.

### Q54. Text augmentation
Synonym replacement, random insertion/deletion, back-translation, token masking, contextual substitution with a masked LM, and LLM-generated paraphrases. Validate label preservation.

### Q55. Language detection and multilingual models
fastText `lid`, `langdetect`. Multilingual models (mBERT, XLM-R, mT5, multilingual E5, LLMs) share representations across languages and enable zero-shot cross-lingual transfer, often weaker for low-resource languages.

### Q56. Hinglish / code-mixed text
Romanised Hindi mixed with English breaks standard tokenisers and vocabularies. Approaches: transliteration + normalisation, multilingual or code-mixed pre-trained models (IndicBERT, MuRIL), subword/char-level features, and domain-specific data.

### Q57. Spelling noise and normalisation
Lowercasing (if appropriate), repeated-character collapsing ("soooo"), slang dictionaries, spell correctors (SymSpell), emoji mapping, and robust subword models.

### Q58. Regex and rule-based NLP
Regex for emails, phone numbers, dates, IDs; spaCy `Matcher`/`PhraseMatcher` for token patterns; gazetteers. Rules are precise and explainable; combine with ML for recall.

### Q59. Evaluating NLP classifiers properly
Stratified splits, macro/micro/weighted F1, per-class precision/recall, confusion matrix, error analysis by length/domain/language, calibration, and a baseline (TF-IDF + LR).

### Q60. Reproducible NLP experiments
Fix seeds, store tokenizer + model version, log hyper-parameters and data hash, and avoid test-set tuning. Save the exact preprocessing code used in training for inference.

# 🟡 Part 3: Mid (3–5 years)

### Q61. Transformer architecture details *(Must-know)*
Embeddings + positional information → N blocks of (multi-head self-attention → add & norm → feed-forward → add & norm). Multi-head attention uses several `Q,K,V` projections to capture different relations. Encoder: bidirectional; decoder: causal mask + (optionally) cross-attention to the encoder.

### Q62. Encoder-only, decoder-only, encoder-decoder
| Family | Examples | Best for |
|---|---|---|
| Encoder-only | BERT, RoBERTa, DeBERTa, XLM-R | Classification, NER, embeddings, re-ranking |
| Decoder-only | GPT, Llama, Mistral, Qwen | Generation, chat, in-context learning |
| Encoder-decoder | T5, BART, mT5 | Translation, summarisation, text-to-text |

### Q63. Pre-training objectives
MLM (BERT), causal LM (GPT), span corruption (T5), denoising (BART), replaced-token detection (ELECTRA), next-sentence/sentence-order prediction (BERT/ALBERT), contrastive objectives for embeddings.

### Q64. Positional encodings
Sinusoidal, learned absolute, relative bias (T5), **RoPE** (rotary, most modern LLMs), ALiBi. They determine how well models extrapolate to longer context.

### Q65. Context length and long documents
Quadratic attention limits context. Options: chunking with overlap, hierarchical models, long-context models (RoPE scaling, sliding-window, Longformer/BigBird), retrieval (RAG), summarise-then-answer. Beware "lost in the middle" degradation.

### Q66. Parameter-efficient fine-tuning (PEFT) *(Must-know)*
LoRA/QLoRA, adapters, prefix/prompt tuning train a tiny set of parameters on a frozen base model, cutting memory and enabling many task-specific adapters.
```python
from peft import LoraConfig, get_peft_model
cfg = LoraConfig(r=16, lora_alpha=32, target_modules=["q_proj", "v_proj"], lora_dropout=0.05, task_type="CAUSAL_LM")
model = get_peft_model(base, cfg)
```

### Q67. Instruction tuning and RLHF/DPO
Supervised fine-tuning on (instruction, response) pairs teaches following instructions. Preference optimisation (RLHF with PPO, DPO, KTO) aligns outputs with human preferences (helpfulness, safety). See `../11_Generative_AI/066_LLM-and-RAG.md`.

### Q68. In-context learning and prompting
Few-shot examples in the prompt steer LLMs without weight updates. Techniques: clear instructions, role, delimiters, examples, structured output (JSON schema), chain-of-thought, self-consistency. Prompts need versioning and tests. See `../11_Generative_AI/064_Prompt-Engineering.md`.

### Q69. When to fine-tune vs prompt vs RAG *(Must-know)*
| Need | Best option |
|---|---|
| New knowledge, frequently changing | RAG |
| Style, format, domain behaviour | Fine-tuning (SFT/LoRA) |
| Quick prototype | Prompting |
| Strict structured output | Constrained decoding / JSON mode + validation |
| Cheap, high-volume classification | Small fine-tuned encoder |

### Q70. RAG pipeline *(Must-know)*
Ingest → clean → **chunk** → embed → index (vector DB) → query rewrite → retrieve (hybrid) → **re-rank** → build prompt with citations → generate → verify/guardrails → log. Failures usually come from retrieval/chunking, not the LLM.

### Q71. Chunking strategies
Fixed-size with overlap, sentence/paragraph-based, semantic (embedding similarity), structure-aware (headings, tables, code), parent-document retrieval (retrieve small, return larger context). Tune chunk size (e.g., 200–800 tokens) with retrieval metrics.

### Q72. Retrieval evaluation
Recall@k, MRR, nDCG, hit rate on a labelled query set; answer-level metrics: faithfulness/groundedness, answer relevance, context precision/recall (RAGAS-style), plus human review.

### Q73. Embedding model selection
Check MTEB-style benchmarks **for your language/domain** (verify current leaders), dimension, max tokens, latency/cost, multilingual support, licence, and whether it needs query/document prefixes. Evaluate on your own queries. Normalise vectors for cosine/dot-product indexes.

### Q74. Vector search basics
Approximate nearest neighbour indexes (HNSW, IVF, PQ) trade recall for speed/memory. Metadata filtering, hybrid search, and index refresh strategy matter in production. See `../11_Generative_AI/067_Vector-Databases.md`.

### Q75. Hallucination: causes and mitigations *(Must-know)*
Causes: missing knowledge, outdated data, ambiguous prompts, decoding randomness, retrieval failures, training bias towards fluent answers. Mitigations: RAG with citations, "answer only from context", lower temperature, verification (NLI/self-check), tool use, refusal behaviour, evaluation sets with unanswerable questions.

### Q76. Structured extraction with LLMs
Define a JSON schema (Pydantic), use function calling/JSON mode, validate and retry on failure, normalise entities, and measure field-level precision/recall against labelled samples.

### Q77. Prompt injection in NLP systems
Untrusted text (web pages, emails, PDFs) can contain instructions that hijack the model. Mitigate: separate instructions from data, least-privilege tools, output validation, allow-lists, human approval for risky actions, and red-teaming. See `../11_Generative_AI/072_LLM-Evaluation-and-Guardrails.md`.

### Q78. Evaluating LLM outputs
Task-specific golden sets, exact-match/F1 where possible, LLM-as-judge with calibration against humans, pairwise comparisons, rubric scoring, regression suites on prompt/model changes, and online metrics (resolution rate, CSAT).

### Q79. Semantic similarity pitfalls
Embedding similarity measures topical closeness, not truth or entailment ("Paris is in France" vs "Paris is not in France" can be close). Use NLI/cross-encoders for contradiction or fine-grained matching.

### Q80. Named entity linking and normalisation
Map mentions to canonical IDs (knowledge base, product catalogue): candidate generation → disambiguation by context → NIL handling. Needed for analytics and search.

### Q81. Handling long-tail and rare entities
Gazetteers, dictionary features, subword models, data augmentation, active learning on low-confidence entities, and retrieval-augmented NER.

### Q82. Annotation and data quality
Write clear guidelines, run pilots, measure **inter-annotator agreement** (Cohen's/Fleiss' kappa, Krippendorff's alpha), adjudicate disagreements, and sample for QA. Label noise caps model quality.

### Q83. Active learning and weak supervision
Select the most uncertain/diverse examples for labelling; use labelling functions/heuristics (Snorkel), LLM pre-labelling with human review, and iterate. Large savings in labelling cost.

### Q84. Domain adaptation
Continue pre-training on in-domain text (DAPT/TAPT), fine-tune with domain data, add domain vocabulary, or use retrieval. Evaluate on domain-specific test data (legal, medical, finance).

### Q85. Multilingual evaluation pitfalls
Benchmarks are English-heavy; tokenisation fertility (tokens per word) is worse for Indic scripts → higher cost and shorter effective context. Evaluate per language, include code-mixed data, and test transliterated input.

### Q86. Indic NLP landscape
Resources: AI4Bharat (IndicBERT, IndicTrans2, IndicNLP), MuRIL, IndicBART, Sarvam and other Indic LLMs (verify current options). Issues: script diversity, transliteration, limited labelled data, dialects.

### Q87. Speech-to-text and NLP pipelines
ASR (Whisper, wav2vec2) → punctuation/normalisation → NLP (intent, NER, summarisation). ASR errors propagate; use confidence scores, domain vocabulary and robust models. WER measures ASR quality.

### Q88. Conversational AI components
Intent classification, slot filling, dialogue state tracking, retrieval/knowledge, response generation, guardrails, handoff to humans. LLM-based agents replace several modules but still need evaluation, memory management and tool control.

### Q89. Latency and cost optimisation for NLP inference
Distil to small encoders, quantise (INT8/INT4), ONNX/TensorRT, batching, caching embeddings/results, truncation, smaller context via retrieval, routing easy queries to cheaper models, streaming outputs.

### Q90. Monitoring NLP systems
Track input length/language distribution, vocabulary drift, embedding drift, prediction distribution, confidence, user feedback, latency/cost, failure rates, and periodic human-labelled audits.

# 🟠 Part 4: Senior (5–7 years)

### Q91. Design a production text-classification system
Requirements (labels, SLA, volume, languages) → baseline (TF-IDF+LR) → fine-tune a compact encoder (DistilBERT/DeBERTa/MiniLM) → calibration + thresholds → active-learning loop → batch/real-time serving (ONNX) → monitoring (drift, per-class metrics) → retraining pipeline → human-in-the-loop for low confidence.

### Q92. Design a semantic search / RAG system for enterprise documents
Connectors & ACL-aware ingestion → parsing (PDF/table/OCR) → chunking with metadata → hybrid index (BM25 + vectors) → query understanding → retrieval → cross-encoder re-ranking → grounded generation with citations → permission filtering at query time → evaluation harness → feedback & analytics → refresh/deletion handling (GDPR).

### Q93. Improve a RAG system that gives wrong answers
Diagnose in order: (1) is the answer in the corpus? (2) did retrieval fetch it (Recall@k)? (3) did re-ranking keep it? (4) did the prompt present it clearly? (5) did the model use it (faithfulness)? Fix chunking, hybrid retrieval, query rewriting, re-ranker, metadata filters, prompt, or model, whichever stage failed.

### Q94. Handling multi-turn conversation in retrieval
Rewrite the latest user message into a standalone query using chat history; keep summaries for long histories; manage memory limits; store entities/preferences explicitly instead of the full transcript.

### Q95. Fine-tuning an LLM with LoRA: end-to-end plan
Define task and eval set → curate high-quality instruction data (hundreds–thousands, diverse) → pick a base model (licence, size, language) → train QLoRA with a small LR, packing, proper chat template and loss masking on responses → evaluate vs prompt/RAG baselines and regression tests → merge or serve adapters → monitor and iterate. Beware overfitting and format drift.

### Q96. Chat templates and loss masking
Use the model's official chat template (system/user/assistant tokens). Compute loss only on assistant tokens. Template mismatch between training and inference silently degrades quality.

### Q97. Dealing with label noise and ambiguity in subjective tasks
Multi-annotator labels (soft labels), calibrated confidence, ordinal approaches, abstention classes, guideline refinement, and reporting agreement ceilings. Model accuracy can't exceed annotator agreement meaningfully.

### Q98. Evaluation design for generative NLP
Build task-specific test sets with edge cases, adversarial/unanswerable questions, multilingual and code-mixed samples; combine automatic metrics, LLM judges (with bias checks: position, verbosity, self-preference), and human review; track regressions per release.

### Q99. LLM-as-judge: biases and safeguards
Biases: position bias, verbosity bias, self-preference, style over substance. Safeguards: randomised order, rubrics, reference answers, multiple judges, agreement with human labels on a calibration set, and periodic human audits.

### Q100. Tokenisation cost and fairness
Different languages need different token counts for the same content. Higher fertility means higher API cost, latency and less usable context. Consider language-specific tokenizers/models, compact prompts, and cost monitoring by language.

### Q101. Bias, fairness and toxicity

### Q102. Privacy and PII in text pipelines

### Q103. Long-document understanding

### Q104. Document parsing quality

### Q108. Distillation for NLP

### Q109. Continual and incremental learning in NLP

### Q110. Safety layers for LLM applications

### Q111. Cost control in LLM-based NLP
Prompt compression, caching (exact and semantic), model routing (small → large), batching, shorter outputs, distillation to task-specific models, async/batch APIs, and per-feature cost dashboards.

### Q112. Sequence length vs batch trade-offs in training

### Q113. Calibration of NLP classifiers

### Task 7. Chunk text with overlap (token-aware)
```python
def chunk(text, tok, size=300, overlap=50):
    ids = tok.encode(text, add_special_tokens=False)
    step = size - overlap
    return [tok.decode(ids[i:i + size]) for i in range(0, max(len(ids) - overlap, 1), step)]
```

# 🐞 Part 7: Debugging Scenarios

### D1. TF-IDF model scores 99% in validation but fails in production
Likely duplicates/leakage across splits, label-revealing tokens (e.g., template text, agent names), or fitting the vectoriser on all data. Deduplicate, split by group/time, inspect top features.

### D2. BERT predicts the same class for everything
Learning rate too high/low, label mapping bug, class imbalance, too few epochs, frozen model unintentionally, or truncated inputs removing signal. Overfit a small batch; check label distribution and tokenisation.

### D3. NER labels misaligned with subword tokens
Forgot to align labels after tokenisation (`word_ids()`), so labels shift. Align to the first sub-token and use `-100` for the rest; verify on a few samples.

### D4. Good on English, poor on Hinglish/Hindi
Tokenizer fragmentation, no code-mixed training data, script/transliteration variants. Add transliteration normalisation, use multilingual/Indic models, and fine-tune on code-mixed data.

### D5. Embedding search returns irrelevant results
Wrong model for domain/language, unnormalised vectors with the wrong metric, chunks too large/small, missing query/document prefixes, stale index. Evaluate Recall@k on labelled queries; try hybrid + re-ranker.

### D6. RAG answers contradict the documents
Context not retrieved or truncated, too many chunks diluting attention, temperature too high, prompt allows outside knowledge. Strengthen the "answer only from context" instruction, add re-ranking, citations and faithfulness checks.

### D7. Model output is truncated or repeats
`max_new_tokens` too low, context overflow, greedy decoding loops. Set stop tokens, repetition penalty/no-repeat n-grams, and use sampling parameters suited to the task.

### D8. GPU out-of-memory when fine-tuning on long text
Reduce `max_length`/batch, use gradient accumulation, mixed precision, gradient checkpointing, LoRA/QLoRA, and length-bucketed batching.

### D9. Tokenizer/model mismatch errors or garbage output
Wrong tokenizer for the checkpoint, missing special tokens after adding vocabulary (forgot `resize_token_embeddings`), chat template not applied. Load tokenizer and model from the same name/revision.

### D10. Classifier is overconfident and wrong
Poor calibration, domain shift. Apply temperature scaling, thresholding with abstention, and collect hard negatives.

### D11. BLEU high but translations are poor
BLEU rewards n-gram overlap, not meaning; check tokenisation/detokenisation consistency (use sacreBLEU), add COMET/human review.

### D12. Sentiment model flips on negation or sarcasm
Limited context features or biased training data. Add negation-heavy examples, use contextual models, and measure on a targeted challenge set.

### D13. Inference latency too high
Long inputs, no batching, large model, CPU-only. Truncate, distil/quantise, ONNX/TensorRT, dynamic batching, cache results, move to GPU.

### D14. Different results between training and serving
Preprocessing/tokenisation mismatch, different library versions, lowercasing differences, truncation/padding side. Export one shared preprocessing function and test parity on a golden set.

### D15. LLM JSON output sometimes invalid
Use schema-constrained decoding or function calling, validate with Pydantic, retry with error feedback, lower temperature, and keep prompts concise.

# 🧩 Part 8: Tricky Questions

### T1. Is stemming or lemmatisation always required?
No. For Transformer models, raw text with the model's tokenizer is better. For TF-IDF baselines it can help a little but may remove useful distinctions.

### T2. Does removing stop words always help?
No. It can destroy negation ("not good"), questions and meaning. It's mainly a bag-of-words trick.

### T3. Are attention weights an explanation?
Not reliably. They show information flow in one layer, not necessarily causal importance.

### T4. Is higher BLEU always better translation?
No. BLEU is a surface-overlap metric; it correlates imperfectly with quality, especially for fluent paraphrases or morphologically rich languages.

### T5. Is cosine similarity high ⇒ same meaning?
Not necessarily. Antonyms and negations can embed near each other. Use NLI/cross-encoders when meaning precision matters.

### T6. Does a bigger context window remove the need for RAG?
No. Cost, latency, "lost in the middle" effects, freshness, access control and citation needs still favour retrieval.

### T7. Can BERT generate text?
Not naturally; it's trained for masked prediction, not left-to-right generation. Decoder or encoder-decoder models are used for generation.

### T8. Why do LLMs struggle with counting letters or arithmetic?
Subword tokenisation hides characters, and next-token prediction isn't exact computation. Tools (code execution, calculators) fix it.

### T9. Is fine-tuning the best way to add knowledge?
Usually not. It's unreliable for facts and hard to update; RAG is better for knowledge, fine-tuning for behaviour/style/format.

### T10. Does lowering temperature to 0 guarantee identical outputs?
Mostly deterministic but not guaranteed (hardware non-determinism, batching, model updates). Don't rely on bitwise reproducibility.

### T11. Is perplexity comparable across models?
Only if they share the same tokenizer/vocabulary and evaluation data; otherwise use bits-per-character/byte.

### T12. Is accuracy a good metric for NER?
No; most tokens are `O`. Use entity-level precision/recall/F1.

### T13. Are LLM judges objective?
No. They have position/verbosity/self-preference biases and must be calibrated against human judgments.

### T14. Does multilingual training always help every language?
No; the "curse of multilinguality" and data imbalance can reduce quality for low-resource languages, and high-resource ones dominate capacity.

### T15. Is adding more training text always better for domain tasks?
Only if relevant and clean. Low-quality or duplicated data can hurt; curation beats volume.

# 🔬 Part 12: Internals

### How TF-IDF is computed in scikit-learn
`idf(t) = ln((1 + N)/(1 + df(t))) + 1` (smooth); `tfidf = tf × idf`; rows are L2-normalised by default, making dot product equal cosine similarity.

### Word2Vec training
Skip-gram with negative sampling maximises `log σ(v_c·v_w) + Σ log σ(−v_n·v_w)` for observed (word, context) pairs and sampled negatives. Embeddings implicitly factorise a shifted PMI matrix.

### BPE algorithm
Initialise vocabulary with bytes/characters → count adjacent pairs → merge the most frequent → repeat until the target vocabulary size. Encoding applies the learned merges in order.

### BERT input
`input_ids` + `token_type_ids` + `attention_mask`; embeddings = token + segment + position, followed by LayerNorm. MLM masks ~15% of tokens (80% `[MASK]`, 10% random, 10% unchanged).

### Self-attention computation
`Q=XW_q`, `K=XW_k`, `V=XW_v`; scores `QKᵀ/√d_k`; mask (padding/causal); softmax; weighted sum with `V`; heads concatenated and projected.

### Autoregressive generation and KV cache
At each step the model outputs logits over the vocabulary for the next token; sampling picks one; it is appended and fed back. Cached keys/values from earlier tokens avoid recomputation.

### Beam search
Maintain `B` best partial sequences by cumulative log-probability; expand each with top tokens; keep the best `B`; apply length normalisation to avoid bias towards short outputs.

### HNSW index
A layered proximity graph: top layers are sparse for coarse navigation; lower layers are denser. Search greedily descends layers; parameters `M`, `efConstruction`, `efSearch` trade recall vs latency/memory.

### CRF decoding
Viterbi dynamic programming finds the best label sequence given emission scores and transition scores, enforcing valid label transitions.

### Dense retrieval training
Contrastive loss (InfoNCE) with in-batch negatives and hard negatives mined from BM25 or earlier models; temperature controls sharpness; symmetric losses help.

# ⚠️ Part 16: Common Mistakes

- Over-cleaning text for Transformers (removing case, punctuation, stop words).
- Fitting TF-IDF/tokenisers on the full dataset before splitting.
- Splitting near-duplicate sentences across train and test.
- Reporting accuracy on imbalanced data or token-level accuracy for NER.
- Using the wrong tokenizer or chat template for a checkpoint.
- Ignoring truncation and silently dropping the important part of long texts.
- Using one chunk size for all document types without evaluating retrieval.
- Skipping a keyword/BM25 component and failing on IDs, codes and rare terms.
- Trusting embedding similarity as proof of meaning.
- Evaluating only in English; not testing code-mixed or low-resource inputs.
- No unanswerable questions in the RAG test set.
- Passing untrusted retrieved text as instructions (prompt injection).
- Fine-tuning for facts instead of retrieval.
- Judging generation by BLEU/ROUGE alone.
- Ignoring PII when logging prompts and outputs.
- Deploying without monitoring for language, length and vocabulary drift.

# 🧾 Part 18: Cheat Sheet & Last-Minute Revision

### Pipeline map
```
Raw text → clean/normalise → tokenise → represent (TF-IDF | embeddings)
        → model (LR | fine-tuned encoder | LLM) → decode/post-process
        → evaluate (task metrics + error analysis) → deploy → monitor
```

### Key formulas
```
tfidf = tf × idf                     cosine(a,b) = a·b / (|a||b|)
attention = softmax(QKᵀ/√d)V        perplexity = exp(cross-entropy)
F1 = 2PR/(P+R)                       BLEU = BP · exp(Σ wₙ log pₙ)
RRF score = Σ 1/(k + rank)
```

### Model picking
- Small data, quick win → TF-IDF + LR/SVM.
- Accuracy on understanding tasks → fine-tuned encoder (DeBERTa/RoBERTa/XLM-R).
- Generation, chat → decoder LLM (prompt, RAG, LoRA).
- Search → BM25 + dense + re-ranker.
- Multilingual/Indic → XLM-R/MuRIL/IndicBERT, check tokenisation.

### Fine-tuning defaults (encoder)
LR 2e-5 – 5e-5 • batch 16–32 • 2–4 epochs • warm-up 6–10% • weight decay 0.01 • max_len by data • dynamic padding • evaluate each epoch • early stopping.

### RAG checklist
Clean parsing • sensible chunking + overlap + metadata • hybrid retrieval • re-ranker • query rewriting • grounded prompt with citations • "I don't know" path • eval set with unanswerable queries • ACL filtering • monitoring and feedback.
