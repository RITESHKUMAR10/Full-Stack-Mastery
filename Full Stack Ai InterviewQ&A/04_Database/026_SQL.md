## 🧪 Sample schema used in many answers
```sql
CREATE TABLE departments (
  dept_id   INT PRIMARY KEY,
  dept_name VARCHAR(50) NOT NULL
);
CREATE TABLE employees (
  emp_id     INT PRIMARY KEY,
  name       VARCHAR(100) NOT NULL,
  dept_id    INT REFERENCES departments(dept_id),
  manager_id INT REFERENCES employees(emp_id),
  salary     DECIMAL(10,2) NOT NULL,
  hire_date  DATE NOT NULL
);
CREATE TABLE customers (
  customer_id INT PRIMARY KEY,
  name        VARCHAR(100) NOT NULL,
  email       VARCHAR(255) UNIQUE,
  city        VARCHAR(50)
);
CREATE TABLE orders (
  order_id    INT PRIMARY KEY,
  customer_id INT NOT NULL REFERENCES customers(customer_id),
  order_date  DATE NOT NULL,
  status      VARCHAR(20) NOT NULL,
  amount      DECIMAL(12,2) NOT NULL
);
```
Sample data: `employees` includes **Ritesh Kumar** in dept 10 with salary 90000; `customers` includes Ritesh Kumar with 3 orders.

# 🟢 Part 1: Fresher (0–1 year)

### Q1. What is SQL?
**Structured Query Language**, the standard language to define, query and manage data in **relational databases** (MySQL, PostgreSQL, SQL Server, Oracle, SQLite). It is declarative: you say **what** data you want, and the optimizer decides **how** to get it.

### Q2. What is a database, a table, a row and a column?
A **database** is an organized collection of data. A **table** (relation) stores one entity type. A **row** (tuple/record) is one instance. A **column** (attribute/field) is one property with a data type.

### Q3. What is an RDBMS? What makes a database "relational"?
A relational database management system stores data in tables connected by keys, enforces integrity (constraints), supports SQL and ACID transactions. Relationships are expressed by foreign keys, not by physical pointers.

### Q4. SQL command categories *(Must-know)*
| Category | Meaning | Commands |
|---|---|---|
| DDL | Data Definition | `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `RENAME` |
| DML | Data Manipulation | `INSERT`, `UPDATE`, `DELETE`, `MERGE` |
| DQL | Data Query | `SELECT` |
| DCL | Data Control | `GRANT`, `REVOKE` |
| TCL | Transaction Control | `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `SET TRANSACTION` |

### Q5. Basic `SELECT`
```sql
SELECT name, salary
FROM employees
WHERE dept_id = 10
ORDER BY salary DESC
LIMIT 5;            -- SQL Server: SELECT TOP 5 ... ; standard: FETCH FIRST 5 ROWS ONLY
```

### Q6. Logical order of execution of a query *(Must-know)*
`FROM` (and joins) → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` (aliases, window functions) → `DISTINCT` → `ORDER BY` → `LIMIT/OFFSET`. That is why you cannot use a `SELECT` alias in `WHERE` (but can in `ORDER BY`), and why you filter aggregates with `HAVING`.

### Q7. `WHERE` vs `HAVING`
`WHERE` filters rows **before** grouping and cannot use aggregates. `HAVING` filters groups **after** aggregation.
```sql
SELECT dept_id, COUNT(*) AS cnt
FROM employees
WHERE salary > 50000
GROUP BY dept_id
HAVING COUNT(*) >= 3;
```

### Q8. `INSERT`, `UPDATE`, `DELETE`
```sql
INSERT INTO customers (customer_id, name, email, city)
VALUES (1, 'Ritesh Kumar', 'ritesh@example.com', 'Delhi');

INSERT INTO customers (customer_id, name) VALUES (2, 'A'), (3, 'B');   -- multi-row

UPDATE employees SET salary = salary * 1.10 WHERE dept_id = 10;

DELETE FROM orders WHERE status = 'cancelled' AND order_date < '2024-01-01';
```
Always run a `SELECT` with the same `WHERE` first. A missing `WHERE` changes every row.

### Q9. `DELETE` vs `TRUNCATE` vs `DROP` *(Must-know)*
| | DELETE | TRUNCATE | DROP |
|---|---|---|---|
| Type | DML | DDL (mostly) | DDL |
| Removes | chosen rows | all rows | table itself |
| `WHERE` allowed | yes | no | no |
| Logging | row by row | minimal | n/a |
| Triggers fire | yes | no | no |
| Resets identity | no | usually yes | n/a |
| Rollback | yes | depends (PostgreSQL/SQL Server yes in transaction; MySQL/Oracle implicit commit) | depends |

### Q10. Data types (common)
Numeric: `INT`, `BIGINT`, `DECIMAL(p,s)`/`NUMERIC`, `FLOAT/DOUBLE`. Text: `CHAR(n)` (fixed), `VARCHAR(n)`, `TEXT`. Date/time: `DATE`, `TIME`, `TIMESTAMP`/`DATETIME`, `TIMESTAMPTZ`. Others: `BOOLEAN`, `JSON/JSONB`, `UUID`, `BLOB/BYTEA`. Use `DECIMAL` for money, never `FLOAT`.

### Q11. `CHAR` vs `VARCHAR`
`CHAR(n)` is fixed length, padded with spaces; good for fixed-size codes. `VARCHAR(n)` stores only the actual length plus a small header. Use `VARCHAR` for most text.

### Q12. What is NULL? *(Must-know)*
"Unknown / missing" value, not zero and not an empty string. Comparisons with NULL give UNKNOWN (neither true nor false): `NULL = NULL` is not true. Use `IS NULL` / `IS NOT NULL`.
```sql
SELECT * FROM employees WHERE manager_id IS NULL;
SELECT COALESCE(manager_id, 0) FROM employees;       -- first non-null
SELECT NULLIF(a, 0) FROM t;                          -- returns NULL if a = 0 (avoids divide by zero)
```
Aggregates (except `COUNT(*)`) ignore NULLs. `NOT IN` with a NULL in the list returns no rows (a classic trap, see Q71).

### Q13. Keys: primary, foreign, unique, candidate, composite, surrogate *(Must-know)*
- **Primary key**: uniquely identifies a row; not null; one per table.
- **Foreign key**: references a key in another table; enforces referential integrity.
- **Unique key**: unique values; allows NULL (rules vary: PostgreSQL/MySQL allow multiple NULLs; SQL Server allows one).
- **Candidate key**: any minimal column set that could be the primary key.
- **Composite key**: more than one column.
- **Surrogate key**: artificial id (auto-increment, UUID) vs **natural key** (real-world value like email).

### Q14. Constraints
`NOT NULL`, `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY ... ON DELETE CASCADE | SET NULL | RESTRICT | NO ACTION`, `CHECK (salary > 0)`, `DEFAULT`.
```sql
CREATE TABLE products (
  product_id INT PRIMARY KEY,
  sku        VARCHAR(30) UNIQUE NOT NULL,
  price      DECIMAL(10,2) CHECK (price >= 0),
  stock      INT DEFAULT 0
);
```
(`CHECK` is enforced in MySQL 8.0.16+; older MySQL ignored it.)

### Q15. Auto-increment / identity columns
MySQL: `AUTO_INCREMENT`. PostgreSQL: `GENERATED ALWAYS AS IDENTITY` (preferred) or `SERIAL`. SQL Server: `IDENTITY(1,1)`. Oracle 12c+: identity columns / sequences. Gaps in values are normal (rollbacks, failed inserts).

### Q16. Filtering operators
```sql
WHERE salary BETWEEN 50000 AND 90000          -- inclusive
WHERE dept_id IN (10, 20)
WHERE name LIKE 'Rit%'                        -- % any chars, _ one char
WHERE name ILIKE 'rit%'                       -- PostgreSQL case-insensitive
WHERE hire_date >= '2024-01-01' AND hire_date < '2025-01-01'
WHERE NOT (status = 'cancelled')
```
Prefer half-open date ranges (`>= start AND < next_start`) over `BETWEEN` for timestamps.

### Q17. `ORDER BY`, `LIMIT`, pagination
```sql
SELECT * FROM orders ORDER BY order_date DESC, order_id DESC LIMIT 10 OFFSET 20;
```
Without `ORDER BY`, row order is not guaranteed. Always add a unique tie-breaker for stable pagination. Deep `OFFSET` is slow (see keyset pagination in Q84).

### Q18. `DISTINCT`
Removes duplicate rows from the result.
```sql
SELECT DISTINCT city FROM customers;
SELECT COUNT(DISTINCT customer_id) FROM orders;
```

### Q19. Aggregate functions
`COUNT`, `SUM`, `AVG`, `MIN`, `MAX` (plus `STRING_AGG`/`GROUP_CONCAT`, `ARRAY_AGG`). `COUNT(*)` counts rows; `COUNT(col)` counts non-null values; `COUNT(DISTINCT col)` counts distinct non-null values.

### Q20. `GROUP BY`
Groups rows sharing values and applies aggregates per group. Every non-aggregated column in `SELECT` must be in `GROUP BY` (standard SQL; MySQL without `ONLY_FULL_GROUP_BY` is lenient and can return arbitrary values).
```sql
SELECT customer_id, COUNT(*) AS orders, SUM(amount) AS total
FROM orders GROUP BY customer_id;
```

### Q21. Aliases
```sql
SELECT e.name AS employee, d.dept_name AS department
FROM employees AS e JOIN departments d ON d.dept_id = e.dept_id;
```
Aliases improve readability and are required for self-joins and derived tables.

### Q22. What is a JOIN? Types *(Must-know)*
Combines rows from two tables on a condition.
- **INNER JOIN**: only matching rows.
- **LEFT (OUTER) JOIN**: all rows from the left, matches from the right (NULL if none).
- **RIGHT (OUTER) JOIN**: mirror of left.
- **FULL (OUTER) JOIN**: all rows from both (not in MySQL; emulate with `UNION` of left and right joins).
- **CROSS JOIN**: Cartesian product (m × n rows).
- **SELF JOIN**: a table joined to itself.
```sql
SELECT c.name, o.order_id, o.amount
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id;
```

### Q23. Find rows with no match (anti-join)
```sql
SELECT c.*
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;                  -- customers without orders
-- equivalent and often clearer:
SELECT * FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
```

### Q24. Self join: employee and manager
```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.emp_id = e.manager_id;
```

### Q25. `UNION` vs `UNION ALL`; `INTERSECT`, `EXCEPT`
`UNION` removes duplicates (sorting/hash cost); `UNION ALL` keeps all rows and is faster. `INTERSECT` = rows in both. `EXCEPT` (`MINUS` in Oracle) = rows in the first but not in the second. Column counts and compatible types must match. MySQL 8.0.31+ supports `INTERSECT/EXCEPT`.

### Q26. Subquery basics
A query inside another query.
```sql
SELECT name FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);            -- scalar subquery
SELECT name FROM employees
WHERE dept_id IN (SELECT dept_id FROM departments WHERE dept_name LIKE 'Eng%');
```
Types: scalar (one value), row, table (derived table in `FROM`), correlated (references the outer query).

### Q27. `IN` vs `EXISTS`
`EXISTS` stops at the first match and handles NULLs safely; `IN` compares against a list/set. Modern optimizers often rewrite them to the same plan, but `NOT EXISTS` is safer than `NOT IN` when NULLs are possible.

### Q28. String functions
`CONCAT`, `||` (PostgreSQL/Oracle/SQLite), `UPPER`, `LOWER`, `TRIM`, `SUBSTRING`/`SUBSTR`, `LENGTH`/`CHAR_LENGTH`, `REPLACE`, `POSITION`/`INSTR`, `LEFT`, `RIGHT`, `LPAD`, `REGEXP`/`~`.
```sql
SELECT UPPER(name), LENGTH(name), SUBSTRING(email FROM POSITION('@' IN email) + 1) AS domain
FROM customers;
```

### Q29. Date and time functions (differences by dialect)
| Task | PostgreSQL | MySQL | SQL Server |
|---|---|---|---|
| Now | `NOW()` | `NOW()` | `GETDATE()` / `SYSDATETIME()` |
| Add 7 days | `d + INTERVAL '7 days'` | `d + INTERVAL 7 DAY` | `DATEADD(day, 7, d)` |
| Difference | `d2 - d1` / `AGE()` | `DATEDIFF(d2, d1)` | `DATEDIFF(day, d1, d2)` |
| Truncate | `DATE_TRUNC('month', d)` | `DATE_FORMAT(d, '%Y-%m-01')` | `DATETRUNC` (2022+) |
| Extract | `EXTRACT(YEAR FROM d)` | `YEAR(d)` / `EXTRACT` | `YEAR(d)` / `DATEPART` |
Store timestamps in UTC (`TIMESTAMPTZ` in PostgreSQL) and convert at the edges.

### Q30. `CASE` expression
```sql
SELECT name, salary,
  CASE
    WHEN salary >= 100000 THEN 'High'
    WHEN salary >= 50000  THEN 'Medium'
    ELSE 'Low'
  END AS band
FROM employees;
```
Conditional aggregation:
```sql
SELECT dept_id,
  SUM(CASE WHEN status = 'paid' THEN amount ELSE 0 END) AS paid_total
FROM orders GROUP BY dept_id;
```

### Q31. `COALESCE`, `NULLIF`, `IFNULL`/`ISNULL`
`COALESCE(a, b, c)` is standard and returns the first non-NULL. `IFNULL` (MySQL/SQLite), `ISNULL` (SQL Server), `NVL` (Oracle) are two-argument vendor versions.

### Q32. Type casting
```sql
SELECT CAST('123' AS INT);
SELECT '123'::INT;                       -- PostgreSQL shortcut
SELECT CONVERT(INT, '123');              -- SQL Server
```
Implicit casts in `WHERE` (comparing a string column to a number) can disable index use.

### Q33. Views
A saved query that behaves like a virtual table.
```sql
CREATE VIEW v_active_customers AS
SELECT c.customer_id, c.name, COUNT(o.order_id) AS orders
FROM customers c JOIN orders o USING (customer_id)
GROUP BY c.customer_id, c.name;
```
Benefits: abstraction, security (expose limited columns), reuse. Views do not store data (except materialized views) and are not automatically faster.

### Q34. Indexes (intro) *(Must-know)*
A data structure (usually a B-tree) that speeds up lookups, joins and sorting at the cost of extra storage and slower writes.
```sql
CREATE INDEX idx_orders_customer_date ON orders (customer_id, order_date);
CREATE UNIQUE INDEX uq_customers_email ON customers (email);
```
Primary keys and unique constraints create indexes automatically. Do not index everything.

### Q35. Clustered vs non-clustered index
Clustered: table rows are physically ordered by the index key (one per table; SQL Server, InnoDB primary key). Non-clustered: separate structure with pointers to rows. PostgreSQL tables are heap-organized (no clustered index by default; `CLUSTER` is a one-time reorder).

### Q36. What is normalization? Normal forms *(Must-know)*
Organizing data to reduce redundancy and update anomalies.
- **1NF**: atomic values, no repeating groups.
- **2NF**: 1NF + no partial dependency on part of a composite key.
- **3NF**: 2NF + no transitive dependency (non-key columns depend only on the key).
- **BCNF**: every determinant is a candidate key.
Denormalization deliberately adds redundancy to speed reads (reporting, caching), with a maintenance cost.

### Q37. Transactions and ACID *(Must-know)*
A transaction is a unit of work that either fully completes or not at all.
- **Atomicity**: all or nothing.
- **Consistency**: moves the database between valid states (constraints hold).
- **Isolation**: concurrent transactions do not interfere improperly.
- **Durability**: committed data survives crashes (write-ahead log).
```sql
BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;      -- or ROLLBACK;
```

### Q38. Relationships: one-to-one, one-to-many, many-to-many
One-to-many: foreign key on the "many" side (`orders.customer_id`). Many-to-many: junction table with two foreign keys (`student_courses(student_id, course_id)` with a composite primary key). One-to-one: unique foreign key or shared primary key.

### Q39. `ALTER TABLE` essentials
```sql
ALTER TABLE customers ADD COLUMN phone VARCHAR(20);
ALTER TABLE customers ALTER COLUMN city SET NOT NULL;        -- PostgreSQL
ALTER TABLE customers MODIFY city VARCHAR(80) NOT NULL;      -- MySQL
ALTER TABLE customers DROP COLUMN phone;
ALTER TABLE orders ADD CONSTRAINT fk_cust FOREIGN KEY (customer_id) REFERENCES customers(customer_id);
```
Large `ALTER`s can lock tables; plan online schema changes.

### Q40. SQL injection and parameterized queries *(Must-know)*
Attack: user input concatenated into SQL (`"... WHERE name = '" + input + "'"` with input `' OR '1'='1`). Prevention: **prepared statements / parameterized queries**, ORMs used correctly, least-privilege DB accounts, input validation, no dynamic identifiers from user input without whitelisting.
```js
db.query("SELECT * FROM users WHERE email = $1", [email]);
```

# 🔵 Part 2: Junior (1–3 years)

### Q41. `INNER JOIN` vs `WHERE` filter on a `LEFT JOIN` *(Must-know)*
Putting a right-table condition in `WHERE` turns a LEFT JOIN into an INNER JOIN, because NULL rows fail the condition.
```sql
-- Loses customers without paid orders:
SELECT c.name, o.order_id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'paid';
-- Keeps all customers:
SELECT c.name, o.order_id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id AND o.status = 'paid';
```

### Q42. Join with multiple tables and `USING` / `NATURAL JOIN`
```sql
SELECT c.name, o.order_id, p.name AS product
FROM customers c
JOIN orders o USING (customer_id)
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id;
```
`USING` merges the shared column. Avoid `NATURAL JOIN` (silent breakage when columns are added).

### Q43. Duplicate rows from joins ("fan-out")
Joining one-to-many tables multiplies rows and inflates `SUM`. Aggregate in a subquery/CTE first, then join.
```sql
SELECT c.customer_id, SUM(o.amount) AS order_total, COALESCE(p.paid, 0) AS paid
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
LEFT JOIN (SELECT customer_id, SUM(amount) AS paid FROM payments GROUP BY customer_id) p
       ON p.customer_id = c.customer_id
GROUP BY c.customer_id, p.paid;
```

### Q44. Top-N per group *(Must-know)*
Highest paid employee per department with a window function:
```sql
SELECT * FROM (
  SELECT e.*, ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn
  FROM employees e
) t WHERE rn = 1;
```
Use `RANK()` to keep ties, `DENSE_RANK()` for no gaps.

### Q45. Second highest salary (classic)
```sql
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1;

SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS r FROM employees
) t WHERE r = 2 LIMIT 1;
```
The generic Nth version uses `DENSE_RANK()`. Return `NULL` if it does not exist by wrapping in a subquery.

### Q46. Window functions *(Must-know)*
Compute across a set of rows related to the current row **without collapsing** them.
```sql
SELECT name, dept_id, salary,
       AVG(salary) OVER (PARTITION BY dept_id)                  AS dept_avg,
       salary - AVG(salary) OVER (PARTITION BY dept_id)         AS diff,
       RANK()  OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk
FROM employees;
```
Syntax: `function() OVER (PARTITION BY ... ORDER BY ... frame)`.

### Q47. `ROW_NUMBER` vs `RANK` vs `DENSE_RANK` vs `NTILE`
For salaries 100, 100, 90: `ROW_NUMBER` = 1,2,3; `RANK` = 1,1,3; `DENSE_RANK` = 1,1,2; `NTILE(2)` splits rows into 2 buckets.

### Q48. `LAG`, `LEAD`, running totals and moving averages
```sql
SELECT order_date, amount,
       LAG(amount)  OVER (ORDER BY order_date) AS prev_amount,
       LEAD(amount) OVER (ORDER BY order_date) AS next_amount,
       SUM(amount)  OVER (ORDER BY order_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
       AVG(amount)  OVER (ORDER BY order_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma7
FROM daily_sales;
```
Default frame with `ORDER BY` is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, which treats ties as peers; use `ROWS` for exact row-based frames.

### Q49. CTEs (`WITH`) *(Must-know)*
Named temporary result sets that make queries readable.
```sql
WITH monthly AS (
  SELECT DATE_TRUNC('month', order_date) AS m, SUM(amount) AS total
  FROM orders GROUP BY 1
)
SELECT m, total, total - LAG(total) OVER (ORDER BY m) AS change
FROM monthly;
```
PostgreSQL 12+ inlines non-recursive CTEs by default (use `MATERIALIZED` to force). Older versions treated CTEs as optimization fences.

### Q50. Recursive CTE (hierarchies)
```sql
WITH RECURSIVE org AS (
  SELECT emp_id, name, manager_id, 1 AS level
  FROM employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.emp_id, e.name, e.manager_id, o.level + 1
  FROM employees e JOIN org o ON e.manager_id = o.emp_id
)
SELECT * FROM org ORDER BY level;
```
Guard against cycles (path array, depth limit). SQL Server omits the `RECURSIVE` keyword.

### Q51. Correlated subquery
Runs logically once per outer row.
```sql
SELECT e.name, e.salary
FROM employees e
WHERE e.salary > (SELECT AVG(salary) FROM employees WHERE dept_id = e.dept_id);
```
Often faster as a join with a pre-aggregated derived table or a window function.

### Q52. Find duplicates and delete them
```sql
SELECT email, COUNT(*) FROM customers GROUP BY email HAVING COUNT(*) > 1;

DELETE FROM customers c
USING (
  SELECT customer_id,
         ROW_NUMBER() OVER (PARTITION BY email ORDER BY customer_id) AS rn
  FROM customers
) d
WHERE c.customer_id = d.customer_id AND d.rn > 1;      -- PostgreSQL
```
MySQL: `DELETE c FROM customers c JOIN (...) d ON ... WHERE d.rn > 1`. Then add a `UNIQUE` constraint to prevent recurrence.

### Q53. Upsert (insert or update)
```sql
-- PostgreSQL / SQLite
INSERT INTO products (sku, price) VALUES ('A1', 10)
ON CONFLICT (sku) DO UPDATE SET price = EXCLUDED.price;
-- MySQL
INSERT INTO products (sku, price) VALUES ('A1', 10)
ON DUPLICATE KEY UPDATE price = VALUES(price);
-- Standard / SQL Server / Oracle
MERGE INTO products p USING (SELECT 'A1' AS sku, 10 AS price) s ON p.sku = s.sku
WHEN MATCHED THEN UPDATE SET price = s.price
WHEN NOT MATCHED THEN INSERT (sku, price) VALUES (s.sku, s.price);
```

### Q54. `RETURNING` / `OUTPUT`
PostgreSQL: `INSERT ... RETURNING id`, `UPDATE ... RETURNING *`. SQL Server: `OUTPUT inserted.id`. MySQL: use `LAST_INSERT_ID()`. Avoids an extra round trip.

### Q55. Pivot and unpivot
Rotate rows to columns using conditional aggregation (portable):
```sql
SELECT customer_id,
  SUM(CASE WHEN EXTRACT(MONTH FROM order_date) = 1 THEN amount ELSE 0 END) AS jan,
  SUM(CASE WHEN EXTRACT(MONTH FROM order_date) = 2 THEN amount ELSE 0 END) AS feb
FROM orders GROUP BY customer_id;
```
SQL Server/Oracle have `PIVOT`; PostgreSQL has `crosstab()` (tablefunc).

### Q56. `GROUP BY` extensions: `ROLLUP`, `CUBE`, `GROUPING SETS`
```sql
SELECT dept_id, EXTRACT(YEAR FROM hire_date) AS yr, COUNT(*)
FROM employees
GROUP BY ROLLUP (dept_id, EXTRACT(YEAR FROM hire_date));      -- subtotals + grand total
```
MySQL: `GROUP BY ... WITH ROLLUP`. Use `GROUPING()` to distinguish subtotal NULLs.

### Q57. `HAVING` without `GROUP BY`; aggregate filtering tricks
`HAVING` can filter the whole table as one group. `FILTER (WHERE ...)` (PostgreSQL) gives a neat conditional aggregate:
```sql
SELECT COUNT(*) FILTER (WHERE status = 'paid') AS paid_orders FROM orders;
```

### Q58. String aggregation
```sql
SELECT dept_id, STRING_AGG(name, ', ' ORDER BY name) FROM employees GROUP BY dept_id;   -- PostgreSQL, SQL Server 2017+
SELECT dept_id, GROUP_CONCAT(name ORDER BY name SEPARATOR ', ') FROM employees GROUP BY dept_id;  -- MySQL
```

### Q59. `LIKE` performance and full-text search
`LIKE 'abc%'` can use a B-tree index; `LIKE '%abc'` or `'%abc%'` cannot. Use full-text indexes (`MATCH ... AGAINST` MySQL, `tsvector` + GIN PostgreSQL), trigram indexes (`pg_trgm`), or a search engine (Elasticsearch) for text search.

### Q60. Index basics: choosing columns
Index columns used in `WHERE`, `JOIN`, `ORDER BY`, `GROUP BY`; prefer high-selectivity columns; composite indexes follow the **leftmost prefix rule**: index `(a, b, c)` helps filters on `a`, `a,b`, `a,b,c`, not `b` alone. Put equality columns first, then range column, then sort columns.

### Q61. Covering index
An index that contains all columns a query needs, so the table is not touched (index-only scan). Use `INCLUDE` (PostgreSQL 11+, SQL Server) for non-key payload columns.
```sql
CREATE INDEX idx_orders_cust ON orders (customer_id) INCLUDE (amount, order_date);
```

### Q62. When indexes are NOT used
Functions on the column (`WHERE LOWER(email) = ...` unless a functional index exists), implicit type conversion, leading wildcards, `OR` across different columns (sometimes), low selectivity (the planner prefers a scan), stale statistics, `<>`/`NOT IN` patterns, composite index prefix not matched.

### Q63. `EXPLAIN` basics *(Must-know)*
Shows the execution plan the optimizer chose.
```sql
EXPLAIN SELECT * FROM orders WHERE customer_id = 42;
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;       -- PostgreSQL: runs query, shows real times
EXPLAIN ANALYZE SELECT ...;                  -- MySQL 8.0.18+
```
Look for: scan type (Seq Scan vs Index Scan vs Index Only Scan), join algorithm (Nested Loop, Hash Join, Merge Join), estimated vs actual rows, sorts spilling to disk, high cost nodes. `EXPLAIN ANALYZE` actually executes (wrap writes in a transaction and roll back).

### Q64. Joins algorithms
**Nested loop** (good with a small outer set and indexed inner), **hash join** (builds a hash table on the smaller side; good for large unsorted equi-joins), **merge join** (both inputs sorted; good for large sorted/indexed inputs). The optimizer picks by cost estimates.

### Q65. Isolation levels and anomalies *(Must-know)*
| Level | Dirty read | Non-repeatable read | Phantom read |
|---|---|---|---|
| READ UNCOMMITTED | possible | possible | possible |
| READ COMMITTED | no | possible | possible |
| REPEATABLE READ | no | no | possible* |
| SERIALIZABLE | no | no | no |
*MySQL InnoDB's REPEATABLE READ prevents most phantoms with next-key locks; PostgreSQL's REPEATABLE READ is snapshot isolation (no phantoms in practice but allows write skew). Defaults: PostgreSQL/Oracle/SQL Server = READ COMMITTED; MySQL InnoDB = REPEATABLE READ.

### Q66. Locks: shared, exclusive, row vs table, deadlocks
Readers may take shared locks or use MVCC snapshots (PostgreSQL, InnoDB, Oracle). Writers take exclusive row locks. **Deadlock**: two transactions wait on each other's locks; the database kills one victim (retry it). Reduce by consistent access order, short transactions, proper indexes (so fewer rows are locked), and retry logic.

### Q67. MVCC in one paragraph
Multi-Version Concurrency Control keeps multiple versions of rows so readers do not block writers and writers do not block readers. Each transaction sees a consistent snapshot. Cost: old versions need cleanup (PostgreSQL `VACUUM`, InnoDB purge/undo logs).

### Q68. Stored procedures, functions, triggers
- **Procedure**: reusable routine (can modify data, `CALL proc()`).
- **Function**: returns a value, usable in queries.
- **Trigger**: runs automatically on INSERT/UPDATE/DELETE (audit logs, derived columns).
Trade-offs: logic near the data and fewer round trips vs hidden behavior, harder versioning/testing, vendor lock-in. Use triggers sparingly.
```sql
CREATE FUNCTION add_tax(price NUMERIC) RETURNS NUMERIC
LANGUAGE sql IMMUTABLE AS $$ SELECT price * 1.18 $$;     -- PostgreSQL
```

### Q69. Temporary tables, table variables, derived tables
Temp tables live for a session/transaction and can be indexed (good for staging large intermediate results). Derived tables/CTEs are query-scoped. Table variables (SQL Server) have different statistics behavior.

### Q70. Common table design best practices
Primary key on every table; consistent naming (`snake_case`); correct data types and lengths; `NOT NULL` where possible; foreign keys with indexes on the child column; timestamps (`created_at`, `updated_at`); soft delete flag only when needed; avoid storing comma-separated lists in one column; use `DECIMAL` for money; store UTC.

### Q71. `NOT IN` NULL trap *(Must-know)*
```sql
SELECT * FROM a WHERE id NOT IN (SELECT a_id FROM b);   -- if b.a_id has any NULL, returns NO rows
```
Because `id <> NULL` is UNKNOWN. Use `NOT EXISTS` or filter `WHERE a_id IS NOT NULL`.

### Q72. Counting traps
`COUNT(*)` counts all rows; `COUNT(col)` skips NULLs. After a `LEFT JOIN`, `COUNT(*)` counts the unmatched row as 1; use `COUNT(o.order_id)` to count real orders.

### Q73. Date range reporting: orders per day with zero days
Generate a calendar and left join:
```sql
SELECT d::date AS day, COALESCE(COUNT(o.order_id), 0) AS orders
FROM generate_series('2025-01-01'::date, '2025-01-31', '1 day') d      -- PostgreSQL
LEFT JOIN orders o ON o.order_date = d::date
GROUP BY 1 ORDER BY 1;
```
Other engines: recursive CTE or a calendar table.

### Q74. Gaps and islands (consecutive values)
```sql
SELECT MIN(day) AS start_day, MAX(day) AS end_day, COUNT(*) AS streak
FROM (
  SELECT day, day - (ROW_NUMBER() OVER (ORDER BY day))::int AS grp
  FROM logins WHERE user_id = 1
) t GROUP BY grp ORDER BY start_day;
```
Subtracting the row number from a date/integer gives a constant for consecutive runs.

### Q75. JSON in SQL (awareness)
PostgreSQL `JSONB` with operators `->`, `->>`, `@>`, GIN indexes; MySQL `JSON` with `->`, `->>`, `JSON_EXTRACT`, generated columns for indexing; SQL Server `JSON_VALUE`, `OPENJSON`. Use JSON for flexible attributes, not as a replacement for relational structure.

# 🟡 Part 3: Mid (3–5 years)

### Q76. B-tree index internals and cost
A B+tree keeps keys sorted in pages (8 KB PostgreSQL, 16 KB InnoDB). Lookups cost O(log n) page reads (typically 3–4 levels even for hundreds of millions of rows). Range scans follow linked leaf pages. Inserts can split pages (random UUID keys cause more splits and cache misses than sequential keys). Each index adds write cost and storage.

### Q77. Index types beyond B-tree
- **Hash**: equality only (PostgreSQL hash indexes are crash-safe since v10; InnoDB uses an adaptive hash internally).
- **GIN / GiST** (PostgreSQL): arrays, JSONB, full text, geometric.
- **BRIN** (PostgreSQL): tiny block-range index for huge naturally ordered tables (time series).
- **Full-text, spatial (R-tree), bitmap** (Oracle), **columnstore** (SQL Server/analytics).
- **Partial** (`WHERE active`), **expression** (`LOWER(email)`), **covering** (`INCLUDE`).
```sql
CREATE INDEX idx_active_users ON users (email) WHERE active;          -- partial
CREATE INDEX idx_lower_email ON users (LOWER(email));                 -- expression
```

### Q78. Composite index design example
Query: `WHERE customer_id = ? AND status = 'paid' ORDER BY order_date DESC LIMIT 20`.
Best index: `(customer_id, status, order_date DESC)`: equality, equality, then sort column, so the database reads 20 index entries without a sort. Check with `EXPLAIN`.

### Q79. Index selectivity and cardinality
Selectivity = distinct values / rows. A boolean column has low selectivity (a poor standalone B-tree index), but a partial index on the rare value can be excellent. Statistics (`ANALYZE`, `UPDATE STATISTICS`) feed the planner; stale stats cause bad plans.

### Q80. Reading an `EXPLAIN ANALYZE` plan (PostgreSQL)
```
Index Scan using idx_orders_cust on orders  (cost=0.43..8.45 rows=1 width=40) (actual time=0.03..0.04 rows=3 loops=1)
  Index Cond: (customer_id = 42)
Planning Time: 0.1 ms   Execution Time: 0.08 ms
```
Compare estimated `rows` with `actual rows` (big gaps mean bad statistics); check `loops` (nested loop multiplier), `Buffers: shared hit/read`, "Rows Removed by Filter", "Sort Method: external merge Disk" (needs `work_mem`), and "Seq Scan" on large tables.

### Q81. Query optimization checklist *(Must-know)*
1. Measure first (`EXPLAIN ANALYZE`, slow query log, `pg_stat_statements`).
2. Select only needed columns (avoid `SELECT *`).
3. Filter early; make predicates **sargable** (`date_col >= X AND date_col < Y`, not `DATE(date_col) = X`).
4. Add/adjust indexes matching filter + join + sort.
5. Avoid functions on indexed columns; avoid implicit casts.
6. Reduce rows before joining (pre-aggregate).
7. Replace correlated subqueries with joins/windows where helpful.
8. Fix N+1 queries from the application.
9. Update statistics; check configuration (`work_mem`, buffer pool).
10. Consider caching, read replicas, or summary tables.

### Q82. Sargable vs non-sargable predicates
Non-sargable: `WHERE YEAR(order_date) = 2025`, `WHERE amount + 10 > 100`, `WHERE name LIKE '%son'`. Sargable: `WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01'`, `WHERE amount > 90`, `WHERE name LIKE 'son%'`.

### Q83. The N+1 query problem
Application loads N parents then runs one query per parent for children (N+1 round trips). Fix with a join, `IN (...)` batch query, ORM eager loading (`JOIN FETCH`, `include`, `select_related`), or DataLoader batching.

### Q84. Pagination strategies
`OFFSET` is O(offset) (database still reads skipped rows). **Keyset (seek) pagination** is O(log n):
```sql
SELECT * FROM orders
WHERE (order_date, order_id) < ('2025-06-01', 9000)
ORDER BY order_date DESC, order_id DESC
LIMIT 20;
```
Needs a unique ordered key and an index on it. Cannot jump to arbitrary pages; great for infinite scroll and APIs.

### Q85. Bulk loading and batch operations
Use multi-row `INSERT`, `COPY` (PostgreSQL), `LOAD DATA INFILE` (MySQL), `BULK INSERT` (SQL Server). Disable/drop secondary indexes during massive loads, then rebuild. Batch updates/deletes in chunks (e.g. 10,000 rows) to limit lock time, WAL size and replication lag.
```sql
DELETE FROM logs WHERE id IN (SELECT id FROM logs WHERE created_at < now() - interval '90 days' LIMIT 10000);
```

### Q86. Handling concurrent updates: lost update problem
Two transactions read the same balance and overwrite each other. Solutions: atomic update (`UPDATE ... SET balance = balance - 100`), `SELECT ... FOR UPDATE` (pessimistic lock), **optimistic locking** with a version column:
```sql
UPDATE products SET stock = stock - 1, version = version + 1
WHERE id = 7 AND version = 3;       -- check affected rows = 1
```

### Q87. `SELECT ... FOR UPDATE`, `SKIP LOCKED`, `NOWAIT`
`FOR UPDATE` locks selected rows until commit. `SKIP LOCKED` lets workers claim different rows in a job queue table without blocking: 
```sql
SELECT id FROM jobs WHERE status = 'pending' ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED;
```
`NOWAIT` fails immediately if locked. Supported in PostgreSQL 9.5+, MySQL 8+, Oracle, SQL Server (`READPAST`).

### Q88. Savepoints and error handling in transactions
```sql
BEGIN;
INSERT ...;
SAVEPOINT s1;
UPDATE ...;           -- if this fails
ROLLBACK TO SAVEPOINT s1;
COMMIT;
```
In PostgreSQL, an error aborts the whole transaction unless you use a savepoint (ORMs use them for nested transactions).

### Q89. Deadlock example and prevention
T1: update row A then B. T2: update row B then A. Each waits for the other. Prevent: always update in the same order (e.g. sorted by id), keep transactions short, avoid user interaction inside transactions, index foreign keys, and implement retry on deadlock (SQLSTATE 40P01 PostgreSQL, error 1213 MySQL).

### Q90. Foreign keys: indexes, cascade, and performance
Index the **child** foreign key column. Without it, deletes on the parent scan the child table and can lock. `ON DELETE CASCADE` is convenient but can delete large trees unexpectedly; prefer `RESTRICT` and explicit deletes for important data. Some high-scale systems avoid physical FKs and enforce integrity in the application (a trade-off: speed and sharding vs correctness guarantees).

### Q91. Soft delete vs hard delete
Soft delete (`deleted_at`) keeps history and allows undo but complicates queries (every query needs the filter), unique constraints (use partial unique indexes `WHERE deleted_at IS NULL`), and GDPR erasure. Alternatives: archive tables, audit/history tables, temporal tables.

### Q92. Audit and history tables
Use triggers or application events to record changes (who, when, old/new values). SQL Server temporal tables, MariaDB system-versioned tables, and PostgreSQL extensions (`temporal_tables`) track row versions. Consider CDC (change data capture) for downstream systems.

### Q93. Views vs materialized views
Materialized views store query results and must be refreshed (`REFRESH MATERIALIZED VIEW CONCURRENTLY` in PostgreSQL requires a unique index). Good for expensive aggregates read often. Trade-off: staleness vs speed. MySQL has no built-in materialized views; use summary tables updated by jobs/triggers.

### Q94. Partitioning *(Must-know)*
Splitting a large table into smaller physical parts.
- **Range** (by date), **List** (by region), **Hash** (spread evenly).
```sql
CREATE TABLE events (id BIGINT, created_at TIMESTAMPTZ NOT NULL, payload JSONB)
PARTITION BY RANGE (created_at);
CREATE TABLE events_2025_01 PARTITION OF events
  FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
```
Benefits: partition pruning (scan only relevant partitions), fast retention (`DROP` a partition), smaller indexes, maintenance per partition. Costs: primary/unique keys must include the partition key, planning overhead with thousands of partitions.

### Q95. Sharding vs partitioning vs replication
- **Partitioning**: within one database server.
- **Sharding**: spreading data across multiple servers by a shard key (application or middleware routes). Hard: cross-shard joins/transactions, rebalancing, hot shards.
- **Replication**: copies of the same data on other servers for availability and read scaling.

### Q96. Replication types and lag
Primary/replica (leader/follower), **async** (fast, may lose recent commits on failover), **sync/semisync** (safer, higher latency), logical vs physical (WAL/binlog shipping). Reads from replicas can be stale (**replication lag**): use read-your-writes routing for critical flows. Multi-primary adds conflict resolution complexity.

### Q97. Backup and recovery
Logical backups (`pg_dump`, `mysqldump`) vs physical (base backups, snapshots, `xtrabackup`). **Point-in-time recovery (PITR)** replays WAL/binlog to a chosen moment. Define RPO/RTO, test restores regularly, encrypt and store off-site.

### Q98. Connection pooling
Opening connections is expensive (process per connection in PostgreSQL). Use a pool in the app (HikariCP, pg-pool) and/or an external pooler (PgBouncer, ProxySQL, RDS Proxy). Size pools to database capacity (e.g. `cores × 2 + disks` as a start), not to the number of app threads. Too many connections cause memory pressure and context switching.

### Q99. ORM usage and pitfalls
Pros: productivity, migrations, parameterization. Cons: N+1, inefficient generated SQL, over-fetching, hidden transactions, leaky abstractions. Practices: inspect generated SQL, use projections/DTO queries for reports, raw SQL for complex analytics, batch operations, and indexes that match actual queries.

### Q100. Schema migrations in production
Use versioned migrations (Flyway, Liquibase, Alembic, Prisma Migrate). Zero-downtime pattern: **expand → migrate → contract**: add nullable column, deploy code writing both, backfill in batches, switch reads, drop old column later. Avoid long locks (`ALTER TABLE` on big tables): use `CREATE INDEX CONCURRENTLY` (PostgreSQL), online DDL (MySQL `ALGORITHM=INPLACE`), pt-online-schema-change / gh-ost.

### Q101. Data types and storage choices that matter
`BIGINT` for ids that may exceed 2 billion; `TIMESTAMPTZ` for instants; `DECIMAL` for money (or integer cents); `UUID` (v7/ULID are time-ordered and index-friendly vs random v4); avoid `TEXT` for tiny enumerations (use lookup tables, `CHECK`, or enums with care); narrow rows improve cache efficiency.

### Q102. Character sets and collations
UTF-8 (`utf8mb4` in MySQL, not legacy `utf8`) to store emoji and all languages. Collation controls sorting/comparison (case sensitivity, accents). Mismatched collations in joins cause errors or index misses. Decide on one standard per system.

### Q103. Handling time zones
Store UTC (`TIMESTAMPTZ`), convert in the application/UI. `TIMESTAMP` without zone is ambiguous. Daylight saving changes make "daily" boundaries tricky: compute boundaries in the user's zone, then convert to UTC.

### Q104. Row-level security and permissions
`GRANT SELECT ON orders TO analyst;` `REVOKE ...`. Roles for groups. PostgreSQL **Row Level Security** policies restrict visible rows per user (multi-tenant isolation). Use least privilege: the application user should not own the schema or be a superuser.

### Q105. Multi-tenant database designs
Shared table with `tenant_id` (cheapest; need RLS and composite indexes starting with `tenant_id`), schema per tenant (moderate isolation), database per tenant (strongest isolation, higher ops cost). Consider noisy neighbors, backup/restore per tenant, and migration effort.

### Q106. OLTP vs OLAP
OLTP: many small transactions, row stores, normalized, indexes (PostgreSQL, MySQL). OLAP: large scans/aggregations, columnar stores, denormalized star schemas (BigQuery, Snowflake, ClickHouse, Redshift). Use ETL/ELT or CDC to feed analytics instead of running heavy reports on the primary.

### Q107. Star schema basics
A central **fact table** (events/measures: sales amount) with foreign keys to **dimension tables** (date, product, customer, store). Optimized for analytics queries (group by dimensions). Slowly changing dimensions (SCD type 1 overwrite, type 2 versioned rows with `valid_from/valid_to`).

### Q108. Window frame details
`ROWS` counts physical rows; `RANGE` groups peers with equal `ORDER BY` values; `GROUPS` counts peer groups. `FIRST_VALUE`, `LAST_VALUE` (watch the default frame: it ends at the current row, so `LAST_VALUE` needs `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`), `NTH_VALUE`, `PERCENT_RANK`, `CUME_DIST`, `PERCENTILE_CONT`.

### Q109. Median and percentiles
```sql
SELECT PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY salary) AS median FROM employees;   -- PostgreSQL, Oracle, SQL Server (as window)
```
MySQL has no built-in; use `ROW_NUMBER()` and `COUNT()` windows to pick the middle row(s).

### Q110. Handling hierarchical data: models
Adjacency list (`parent_id`, simple, recursive CTE reads), materialized path (`/1/4/9/`, easy subtree with `LIKE`), nested sets (fast subtree reads, hard writes), closure table (all ancestor-descendant pairs; flexible, more storage), PostgreSQL `ltree`. Choose by read/write pattern.

# 🟠 Part 4: Senior (5–7 years)

### Q111. How the optimizer works (cost-based)
Parses SQL → rewrites (view merging, subquery flattening) → enumerates plans (join orders, access paths, join algorithms) → estimates cost using statistics (row counts, histograms, most common values, correlation) → picks the cheapest → executes. Bad estimates (skewed data, correlated columns, parameter sniffing) are the main cause of slow plans. Remedies: extended statistics (PostgreSQL `CREATE STATISTICS`), histograms (MySQL 8), plan hints (sparingly), query rewrites, `ANALYZE`.

### Q112. Parameter sniffing / generic plans
Prepared statements cache plans built for the first parameter values. Skewed data makes the cached plan terrible for other values (SQL Server "parameter sniffing"; PostgreSQL chooses generic vs custom plans after 5 executions). Fixes: `OPTION (RECOMPILE)`, `OPTIMIZE FOR`, `plan_cache_mode`, query rewrite, or different statements for hot values.

### Q113. Query plan stability and regressions
After upgrades, statistics changes or data growth, plans may flip. Track slow queries with `pg_stat_statements`, `auto_explain`, Query Store (SQL Server), performance schema (MySQL). Use baselines, regression tests with realistic data volumes, and alert on p95 latency.

### Q114. Join order and join explosion
With many tables the planner can't try every order (`join_collapse_limit`, `geqo` in PostgreSQL). Reduce join count with pre-aggregation, denormalized read models, or splitting queries. Inspect row estimates at each join to find where estimates diverge.

### Q115. Locking in depth: InnoDB gap locks, next-key locks
Under REPEATABLE READ, InnoDB locks index records plus gaps to prevent phantoms (next-key locks). A range update on a non-indexed column can lock a lot (or the whole table). Use indexes, lower isolation (READ COMMITTED) where acceptable, keep transactions short. PostgreSQL uses row-level locks stored in tuple headers and doesn't use gap locks (SSI for serializable).

### Q116. Serializable snapshot isolation and write skew
Two transactions each read overlapping data and write different rows, together violating a rule (two doctors both go off-call). Snapshot isolation allows it; `SERIALIZABLE` (PostgreSQL SSI) detects and aborts one (retry on serialization failure 40001). Alternatives: lock the guarding row, use constraints/exclusion constraints.

### Q117. Advisory locks and distributed locking
PostgreSQL `pg_advisory_lock(key)`, MySQL `GET_LOCK()`: application-defined locks for coordinating jobs (cron singletons, migrations). Release on session end. For multi-database or multi-service locking use a dedicated coordinator (Redis, etcd, ZooKeeper) with care about fencing tokens.

### Q118. Transaction design patterns
Keep transactions short and small; avoid network calls inside; commit before sending emails or events; use the **outbox pattern** (write the event in the same transaction, publish asynchronously); make operations **idempotent** (unique request ids with `ON CONFLICT DO NOTHING`); retry on serialization failures/deadlocks with backoff.

### Q119. Idempotency keys and exactly-once effects
Store a unique `request_id` with a unique constraint; if the insert conflicts, return the stored result. Combine with the outbox for message publishing. True exactly-once delivery doesn't exist across systems; aim for at-least-once + idempotent consumers.

### Q120. Write-ahead log (WAL) and durability
Changes are written to a sequential log and flushed (`fsync`) before commit returns; data pages are written later (checkpoints). On crash, replay the log. Settings like `synchronous_commit=off` (PostgreSQL), `innodb_flush_log_at_trx_commit=2` trade durability for speed. WAL also powers replication and PITR.

### Q121. Buffer pool / shared buffers and memory tuning
The database caches pages in memory (InnoDB buffer pool commonly 60–75% of RAM on a dedicated host; PostgreSQL `shared_buffers` ~25% plus OS cache). Tune `work_mem` (per sort/hash node, per connection!), `maintenance_work_mem`, `effective_cache_size`, `max_connections`. Monitor cache hit ratio, temp file usage, checkpoint frequency.

### Q122. Vacuum, bloat and autovacuum (PostgreSQL) *(Must-know)*
MVCC leaves dead tuples after updates/deletes. `VACUUM` marks space reusable; `VACUUM FULL` rewrites the table (exclusive lock). Autovacuum must keep up: tune thresholds for hot tables; long-running transactions and replication slots block cleanup and cause bloat. Also prevents transaction ID wraparound. Monitor `pg_stat_user_tables.n_dead_tup`, `age(datfrozenxid)`.

### Q123. InnoDB specifics: clustered primary key, secondary indexes, undo/redo
Rows are stored in the primary key B-tree; secondary indexes store the primary key value (so a wide PK bloats every index). Choose a compact, monotonically increasing PK. Redo log provides durability; undo log supports MVCC and rollback; purge threads clean old versions; long transactions bloat undo.

### Q124. Choosing primary keys: auto-increment vs UUID vs ULID/UUIDv7
Sequential ids: compact, insert-friendly, but guessable and awkward for sharding/merging. UUIDv4: unguessable, globally unique, random inserts fragment indexes (especially InnoDB clustered). UUIDv7/ULID/Snowflake: time-ordered, global uniqueness, good locality. Use bigint ids internally and expose opaque public ids if needed.

### Q125. Handling big tables: archiving and retention
Partition by time and drop old partitions; move cold data to cheaper storage (archive tables, object storage, data lake); batch deletes; keep indexes lean; compress (PostgreSQL TOAST, `pg_squeeze`, InnoDB compression, columnar extensions); document legal retention.

### Q126. Online index and schema change details
PostgreSQL: `CREATE INDEX CONCURRENTLY` (two scans, can fail leaving invalid index to drop), adding a column with a constant default is instant in 11+, `NOT NULL` via `CHECK ... NOT VALID` then `VALIDATE`. MySQL 8: `ALGORITHM=INSTANT` for some column adds, `INPLACE` for many index ops; for others use gh-ost or pt-osc. Always rehearse on production-sized data and watch replication lag.

### Q127. Read scaling patterns
Replicas with read/write splitting, caching (Redis, application caches with invalidation), CQRS read models, materialized views, search indexes (Elasticsearch/OpenSearch), CDN for static content. Address staleness explicitly (read-your-writes, session stickiness).

### Q128. Write scaling patterns
Batching, queues to smooth bursts, partitioning, sharding, append-only/event logs, LSM-based stores for write-heavy workloads, reducing indexes on hot tables, async processing, and moving analytics off OLTP. Note single-primary relational databases scale writes vertically first.

### Q129. CAP theorem and relational databases
In a network partition you choose consistency or availability. Single-node RDBMS: consistent, not partition-tolerant by itself. Replicated systems: sync replication favors consistency (may become unavailable), async favors availability (stale reads, possible data loss). Distributed SQL (CockroachDB, Spanner, YugabyteDB, TiDB) use consensus (Raft/Paxos) for strong consistency with higher latency.

### Q130. SQL vs NoSQL: how to choose
Relational: structured data, joins, transactions, ad-hoc queries, strong consistency. Document (MongoDB): flexible schema, aggregates read as a unit. Key-value (Redis, DynamoDB): massive scale, simple access patterns. Wide-column (Cassandra): write-heavy, time series, multi-region. Graph (Neo4j): relationships. Search (Elasticsearch): text. Start with PostgreSQL unless a specific requirement points elsewhere; polyglot persistence adds operational cost.

### Q131. Time-series data in SQL
Partition by time, BRIN indexes, compression, retention, continuous aggregates (TimescaleDB), downsampling tables. Use `date_bin`/`time_bucket` for rollups; avoid updating old rows.

### Q132. Full-text search in the database
PostgreSQL: `to_tsvector`, `to_tsquery`, GIN index, ranking `ts_rank`, `pg_trgm` for fuzzy. MySQL: `FULLTEXT` indexes with `MATCH ... AGAINST`. For advanced relevance, facets, typo tolerance, scale: Elasticsearch/OpenSearch/Typesense/Meilisearch fed by CDC.

### Q133. Data integrity beyond constraints
Exclusion constraints (no overlapping bookings in PostgreSQL), deferrable constraints (check at commit), triggers for complex rules, generated columns, domains/enums, application validation as a first line (not the only one). Constraints are the last defense against bugs.

### Q134. Security: encryption, masking, auditing
TLS in transit, encryption at rest (TDE, disk/KMS), column-level encryption for sensitive fields, secrets in a vault, rotating credentials, data masking in non-prod, audit logs (pgaudit), least-privilege roles, network isolation (private subnets), SQL injection prevention, row-level security.

### Q135. Observability for databases
Metrics: QPS, latency percentiles, connections, locks/waits, replication lag, cache hit ratio, disk I/O, bloat, slow queries. Tools: `pg_stat_statements`, `pg_stat_activity`, `EXPLAIN`, MySQL performance schema/slow log, Query Store, Percona PMM, Prometheus exporters, APM traces linking queries to endpoints.

### Q136. Diagnosing a slow query in production (method)
1. Identify via slow log/APM/`pg_stat_statements` (total time, mean time, calls).
2. Reproduce with the same parameters; run `EXPLAIN (ANALYZE, BUFFERS)`.
3. Compare estimates vs actual; check indexes, statistics, locks (`pg_locks`, `SHOW ENGINE INNODB STATUS`), waits.
4. Fix the cheapest root cause: rewrite, index, stats, config, data model.
5. Validate with before/after metrics; add a regression guard (tests/alerts).

### Q137. Locks blocking everything: how to find the blocker
```sql
-- PostgreSQL
SELECT pid, usename, state, wait_event_type, wait_event, query
FROM pg_stat_activity WHERE datname = current_database();
SELECT pg_blocking_pids(pid), * FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;
-- MySQL
SELECT * FROM sys.innodb_lock_waits;
```
Terminate carefully (`pg_cancel_backend`, `pg_terminate_backend`, `KILL`). Prevent with timeouts (`lock_timeout`, `statement_timeout`, `idle_in_transaction_session_timeout`).

### Q138. Data modeling for evolving requirements
Prefer explicit columns for known attributes; use JSONB for sparse/variable attributes with generated columns/indexes for hot keys; avoid EAV (entity-attribute-value) except in rare cases; plan migrations; document the model (ERDs, data dictionary).

### Q139. Zero-downtime major upgrades and migrations
Use logical replication to a new version/cluster, dual-write or CDC to sync, validate with shadow reads, switch traffic with a short write freeze, keep rollback path. For PostgreSQL major upgrades: `pg_upgrade --link` (fast, downtime) or logical replication (near-zero downtime). Test extensions and query plans after the upgrade.

### Q140. Data quality and constraints in pipelines
Validate at ingestion (schemas, `CHECK`s), use staging tables, idempotent loads (`MERGE`), reconciliation counts, data tests (dbt tests, Great Expectations), lineage, and alert on anomalies.

# 🐞 Part 7: Debugging Scenarios

### D1. Query returns too many rows after a join
Fan-out from a one-to-many join or a missing join condition (accidental cross join). Check join keys, add `COUNT(*)` before/after each join, aggregate before joining.

### D2. `LEFT JOIN` behaves like `INNER JOIN`
A `WHERE` filter on right-table columns removed the NULL rows. Move the condition into the `ON` clause (Q41).

### D3. Sum is inflated
Joined two child tables to the same parent, multiplying rows. Use separate pre-aggregated subqueries (Q43).

### D4. `NOT IN` returns nothing
The subquery contains NULL. Use `NOT EXISTS` (Q71).

### D5. Query is slow only sometimes
Plan flip due to parameter values/statistics, lock waits, cache misses, autovacuum or checkpoints, noisy neighbors. Compare `EXPLAIN` for fast and slow parameter sets; check `pg_stat_activity` waits.

### D6. Query is fast on small data, slow in production
Missing index, sequential scan on a large table, estimated rows far off, sorting on disk, `OFFSET` large. Test with production-sized data.

### D7. Index exists but is not used
Function on the column, type mismatch (string vs int), leading wildcard, low selectivity, stale stats, wrong column order, `OR` conditions, collation difference. Check `EXPLAIN` and fix the predicate or index.

### D8. Duplicate key error on insert
Unique constraint violation. Race condition between check and insert: use `INSERT ... ON CONFLICT`, handle the error, or lock. Check for sequence out of sync after bulk import (`setval` in PostgreSQL).

### D9. Deadlock detected
Read the deadlock log (`log_lock_waits`, `SHOW ENGINE INNODB STATUS`), identify the statements and order, standardize access order, add indexes, shorten transactions, and retry.

### D10. Application hangs; many "idle in transaction" sessions
A code path opened a transaction and didn't commit or roll back (exception, missing `finally`, awaiting an external API). They hold locks and block vacuum. Set `idle_in_transaction_session_timeout`, fix error handling, use pool settings.

### D11. "Too many connections"
Pool misconfiguration, connection leaks, many app instances × pool size exceeds `max_connections`. Use a pooler (PgBouncer/ProxySQL), cap pool sizes, close connections, monitor connection counts.

### D12. Incorrect results with GROUP BY in MySQL
`ONLY_FULL_GROUP_BY` disabled returned arbitrary non-aggregated values. Enable it, or aggregate/`GROUP BY` all selected columns.

### D13. Rounding or money mistakes
`FLOAT` used for money, integer division (`5/2 = 2` in many engines; cast to `NUMERIC`), `ROUND` behavior differences. Use `DECIMAL` and explicit casts.

### D14. Timezone off-by-hours
`TIMESTAMP` without zone interpreted in session time zone; daylight saving; server vs client zone mismatch. Store UTC `TIMESTAMPTZ`, set session zone explicitly.

### D15. Pagination shows duplicates or skips rows
Non-deterministic `ORDER BY` (ties) or data changing between pages. Add a unique tiebreaker; use keyset pagination (Q84).

# 🧩 Part 8: Tricky Questions

### T1. Is `SELECT COUNT(*)` always fast?
No. PostgreSQL must scan visible rows (MVCC), so `COUNT(*)` on large tables is O(n) (an index-only scan helps). MyISAM stored an exact count; InnoDB does not. Use estimates (`pg_class.reltuples`), counters, or summary tables when exactness isn't required.

### T2. Can a primary key be NULL? Can a unique column have multiple NULLs?
Primary key cannot be NULL. Unique columns: PostgreSQL, MySQL, Oracle (single column) allow multiple NULLs; SQL Server allows only one NULL in a unique index (unless filtered).

### T3. `WHERE 1=1` — why?
A convenience for dynamically appending `AND` conditions. It has no performance effect (the optimizer removes it). Prefer query builders with parameters.

### T4. Does the order of conditions in `WHERE` matter?
Not for correctness, and usually not for performance (the optimizer reorders). Order of columns in a composite **index** does matter.

### T5. `DELETE` without `WHERE` on a table with foreign keys
Fails if referenced rows exist (unless `CASCADE`). With `ON DELETE CASCADE` it removes child rows, so a "simple" delete can wipe large data.

### T6. Is `TRUNCATE` rollbackable?
In PostgreSQL and SQL Server inside a transaction: yes. In MySQL and Oracle it causes an implicit commit: no.

### T7. `DISTINCT` vs `GROUP BY`
Often equivalent for deduplication. `GROUP BY` is needed for aggregates. Some optimizers produce different plans; use whichever expresses intent.

### T8. Why does `ORDER BY RAND()` perform badly?
It assigns a random value to every row and sorts: O(n log n) on the entire table. Use keyset sampling, `TABLESAMPLE`, or random id selection with index lookups.

### T9. What is the difference between `RANK` and `ROW_NUMBER` for ties?
`ROW_NUMBER` always gives unique numbers (arbitrary among ties unless a tie-breaker is added). `RANK` gives ties the same number and skips the next numbers.

### T10. What does `SELECT * FROM a, b` do?
A cross join (Cartesian product). With a `WHERE a.id = b.a_id` it is an old-style inner join. Prefer explicit `JOIN ... ON`.

### T11. Why can `UPDATE` be slower than `INSERT` + `DELETE`?
Not generally; but updates of indexed columns update every affected index, and MVCC writes new row versions. Updating many rows in one transaction creates bloat and lock pressure; batch it.

### T12. Are views faster than queries?
No (unless materialized). A normal view is inlined into the outer query. It adds abstraction, not speed.

### T13. Is a foreign key automatically indexed?
Not in PostgreSQL, SQL Server, Oracle (you must create the index on the child column). MySQL InnoDB creates an index on FK columns automatically if none exists.

### T14. Can you have an index on a boolean column?
You can, but a plain index rarely helps (low selectivity). A **partial index** on the rare value is useful.

### T15. How are NULLs ordered?
PostgreSQL/Oracle: NULLs sort last in ASC, first in DESC (configurable with `NULLS FIRST/LAST`). MySQL/SQL Server: NULLs sort first in ASC. Be explicit when it matters.

### T16. Is `SELECT DISTINCT` + `ORDER BY` allowed on non-selected columns?
Not in standard SQL/PostgreSQL (ORDER BY expressions must appear in the select list with DISTINCT). MySQL may allow depending on mode.

### T17. What is a "phantom" read?
A repeated range query returns new rows inserted (and committed) by another transaction. Prevented by SERIALIZABLE (or gap/predicate locking).

### T18. Why can long transactions harm the system?
They hold locks, prevent cleanup of old row versions (bloat, undo growth), delay replication, and increase deadlock risk. Keep them short.

### T19. Difference between `UNION` and `JOIN`?
`UNION` stacks rows vertically from compatible result sets; `JOIN` combines columns horizontally using a relationship.

### T20. What does `COUNT(1)` vs `COUNT(*)` do?
Same result and performance in modern databases. Both count rows. `COUNT(col)` differs by skipping NULLs.

# 🔬 Part 12: Database Internals

### I1. Storage layout: pages, tuples, heaps
Data is stored in fixed-size pages (PostgreSQL 8 KB, InnoDB 16 KB, SQL Server 8 KB). A heap table stores tuples in pages without order; an index entry points to a tuple id (PostgreSQL `ctid`). Large values go out-of-line (TOAST, off-page storage).

### I2. Index structure: B+tree
Internal nodes hold separator keys and child pointers; leaf nodes hold keys plus row pointers (or the row itself in a clustered index) and are linked for range scans. Splits and merges keep the tree balanced. Fill factor controls page headroom for updates.

### I3. Query execution pipeline
Parser → analyzer (name/type resolution) → rewriter → planner/optimizer → executor (iterator/Volcano model: each operator pulls rows from children; vectorized/columnar engines process batches). Plan nodes: scans, joins, aggregates, sorts, limits.

### I4. MVCC implementations
PostgreSQL: new row versions stored in the same heap; `xmin`/`xmax` visibility; vacuum removes dead tuples; HOT updates avoid index updates when possible. InnoDB: updates in place, old versions in undo logs; consistent reads rebuild old versions from undo; purge removes obsolete undo.

### I5. Transaction logs and recovery
ARIES-style write-ahead logging: redo to repeat history, undo to roll back losers after crash. Checkpoints bound recovery time. Group commit batches `fsync`s for throughput.

### I6. Lock manager
Lock modes (shared, exclusive, intention locks in hierarchical locking, update locks in SQL Server), lock queues, wait-for graphs for deadlock detection, lock timeouts, row vs page vs table granularity and escalation (SQL Server).

### I7. Buffer management
Page cache with replacement policy (clock-sweep in PostgreSQL, LRU variants in InnoDB), dirty page tracking, background writer, double-buffering with the OS cache (PostgreSQL relies on both), `O_DIRECT` options.

### I8. Join and aggregation algorithms
Nested loop (index lookups), hash join (build/probe; spills to disk in batches), sort-merge join; hash aggregate vs sort aggregate; external merge sort when data exceeds `work_mem`; parallel query workers for scans/joins/aggregates.

### I9. Statistics
Row counts, distinct counts, histograms, most common values, null fraction, correlation (physical order vs logical). Cardinality estimation assumes column independence unless extended statistics are defined. `ANALYZE` updates them (autovacuum triggers it).

### I10. Replication internals
PostgreSQL streaming replication ships WAL; logical replication decodes WAL into row changes via publications/subscriptions. MySQL replicates binlog events (statement/row/mixed) with GTIDs. Replicas replay changes; lag comes from replay speed, long transactions, I/O.

### I11. Columnar vs row storage
Row stores keep a row's columns together (fast point reads/writes). Column stores keep each column separately (compression, vectorized scans, great for aggregates, poor for single-row updates). Hybrid options exist (HTAP, columnar extensions).

### I12. SQLite, DuckDB and embedded engines
SQLite: serverless single-file database, B-tree storage, one writer at a time (WAL mode helps readers), ideal for local apps and tests. DuckDB: embedded analytical columnar engine. Understand when embedded beats client-server.

| Auto id | `GENERATED ... IDENTITY` | `AUTO_INCREMENT` | `IDENTITY` | identity / sequence |
| Upsert | `ON CONFLICT` | `ON DUPLICATE KEY` | `MERGE` | `MERGE` |
| Case-insens. like | `ILIKE` | default collation | collation | `UPPER()` / `REGEXP_LIKE` |
| Current time | `NOW()` | `NOW()` | `GETDATE()` | `SYSDATE` |
| Boolean | `BOOLEAN` | `TINYINT(1)` | `BIT` | `NUMBER(1)` |

### Normal forms summary
| NF | Rule |
|---|---|
| 1NF | atomic values, no repeating groups |
| 2NF | no partial dependency on composite key |
| 3NF | no transitive dependency |
| BCNF | every determinant is a candidate key |

### Index decision guide
| Need | Index |
|---|---|
| Equality + range + sort | B-tree |
| Equality only | Hash |
| JSON/array/full-text | GIN |
| Geometric/range types | GiST |
| Huge time-ordered table | BRIN |
| Query touches subset of rows | Partial |
| Query on expression | Expression/functional |
| Avoid table lookups | Covering (INCLUDE) |

# 🔮 Part 14: Output & Prediction Questions

### O1.
Table `t(x)` has rows `1, 2, NULL, 3`.
```sql
SELECT COUNT(*), COUNT(x), SUM(x), AVG(x) FROM t;
```
**Output:** `4, 3, 6, 2`. `COUNT(*)` counts rows; `COUNT(x)`, `SUM`, `AVG` ignore NULL (6/3 = 2).

### O2.
```sql
SELECT * FROM t WHERE x NOT IN (1, NULL);
```
**Output:** no rows. `x <> NULL` is UNKNOWN, so no row can satisfy `NOT IN`.

### O3.
Table `a(id)`: 1, 2, 3. Table `b(id)`: 2, 3, 4.
```sql
SELECT a.id, b.id FROM a LEFT JOIN b ON a.id = b.id;
```
**Output:** `(1, NULL), (2, 2), (3, 3)`.

### O4.
Same `a` and `b`:
```sql
SELECT id FROM a UNION SELECT id FROM b;      -- 1,2,3,4
SELECT id FROM a UNION ALL SELECT id FROM b;  -- 1,2,3,2,3,4
SELECT id FROM a INTERSECT SELECT id FROM b;  -- 2,3
SELECT id FROM a EXCEPT SELECT id FROM b;     -- 1
```

### O5.
Salaries: 100, 100, 90, 80.
```sql
SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS dr FROM e;
```
**Output:** `100→1, 100→1, 90→2, 80→3`.

### O6.
```sql
SELECT 10 / 4, 10 % 4, 10.0 / 4;
```
**Output:** PostgreSQL/SQL Server: `2, 2, 2.5` (integer division). MySQL: `2.5000, 2, 2.5000` (`/` is decimal division; use `DIV` for integer).

### O7.
```sql
SELECT NULL = NULL, NULL IS NULL, COALESCE(NULL, 5), NULLIF(3, 3);
```
**Output:** `NULL (unknown), true, 5, NULL`.

### O8.
```sql
SELECT COUNT(*) FROM orders o LEFT JOIN customers c ON c.customer_id = o.customer_id WHERE c.customer_id IS NULL;
```
**Answer:** counts orders whose customer does not exist (orphans), expected 0 when foreign keys are enforced.

### O9.
```sql
SELECT 'a' || NULL;       -- PostgreSQL
SELECT CONCAT('a', NULL); -- MySQL
```
**Output:** PostgreSQL: `NULL` (concatenation with NULL gives NULL). MySQL `CONCAT` also returns `NULL`. In PostgreSQL `CONCAT('a', NULL)` returns `a`; in SQL Server `'a' + NULL` is `NULL` by default.

### O10.
```sql
SELECT ROUND(2.5), ROUND(3.5), ROUND(-2.5);
```
**Output:** PostgreSQL (numeric): `3, 4, -3` (round half away from zero). Some engines/types (floating point) use banker's rounding; check the docs.

### O11.
Table `emp(dept, salary)`: (A,100), (A,200), (B,300).
```sql
SELECT dept, SUM(salary) OVER (PARTITION BY dept) AS s FROM emp;
```
**Output:** `A,300; A,300; B,300`. Window sums keep all rows.

### O12.
```sql
SELECT DISTINCT dept FROM emp ORDER BY dept DESC;
```
**Output:** `B`, then `A`.

# ⚠️ Part 16: Common Mistakes

1. **`SELECT *` in production code** (extra I/O, breaks on schema changes, blocks covering indexes).
2. **Missing `WHERE` on `UPDATE`/`DELETE`.** Run it as a `SELECT` first and use transactions.
3. **`NOT IN` with nullable subqueries.**
4. **Filtering the right table in `WHERE` after a `LEFT JOIN`.**
5. **Joining multiple one-to-many tables and summing** (fan-out).
6. **Using functions on indexed columns** in `WHERE`.
7. **Relying on implicit ordering** without `ORDER BY`.
8. **Using `OFFSET` for deep pagination.**
9. **Storing money in `FLOAT`.**
10. **No indexes on foreign keys** (slow joins and deletes).
11. **Too many indexes** (slow writes, wasted space).
12. **String concatenation to build SQL** (injection risk).
13. **Long transactions and transactions held open during network calls.**
14. **Ignoring NULL semantics** (`= NULL`, `COUNT(col)`, aggregates).
15. **Implicit type conversion** (comparing varchar to int).
16. **Storing comma-separated lists or arrays in a column** for relational data.
17. **No migrations discipline** (manual production changes).
18. **Testing only on tiny datasets.**
19. **Using the superuser for the application.**
20. **Not backing up or never testing restores.**
21. **Choosing UUIDv4 clustered primary keys in InnoDB without considering fragmentation.**
22. **Relying on ORM defaults without inspecting SQL.**

# 🧾 Part 18: Cheat Sheet & Last-Minute Revision

### Query skeleton and order
```sql
SELECT DISTINCT cols/aggregates/windows
FROM t1 JOIN t2 ON ...
WHERE row_filter
GROUP BY cols
HAVING group_filter
ORDER BY cols
LIMIT n OFFSET m;
-- logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

### Patterns to memorize
| Problem | Pattern |
|---|---|
| Top N per group | `ROW_NUMBER() OVER (PARTITION BY g ORDER BY x DESC)` |
| Nth highest | `DENSE_RANK()` |
| Previous / next row | `LAG` / `LEAD` |
| Running total | `SUM() OVER (ORDER BY ...)` |
| Rows without match | `LEFT JOIN ... IS NULL` or `NOT EXISTS` |
| Duplicates | `GROUP BY ... HAVING COUNT(*) > 1` |
| Pivot | `SUM(CASE WHEN ... THEN ... END)` |
| Consecutive runs | row number minus value |
| Hierarchy | recursive CTE |
| Upsert | `ON CONFLICT` / `ON DUPLICATE KEY` / `MERGE` |

### Performance checklist
Select needed columns • sargable filters • indexes on filter/join/sort columns • composite order: equality → range → sort • avoid N+1 • pre-aggregate before joins • keyset pagination • update statistics • read `EXPLAIN ANALYZE`.

### Transaction checklist
Keep short • consistent lock order • use appropriate isolation • retry on deadlock/serialization failure • idempotency keys • outbox for events • timeouts configured.

### Interview strategy
1. Restate the question and clarify the schema (keys, NULLs, duplicates, ties).
2. Write a simple correct query first; name CTEs clearly.
3. Walk through a tiny example to check logic.
4. Discuss indexes/performance and dialect differences.
5. Mention edge cases: empty sets, NULLs, time zones, large data.

### Final checklist before the interview
- [ ] Write joins (including anti-joins), group/having, subqueries and CTEs without hesitation.
- [ ] Use `ROW_NUMBER/RANK/DENSE_RANK/LAG/SUM OVER` for top-N, running totals and comparisons.
- [ ] Explain ACID, isolation levels, MVCC, locks and deadlocks.
- [ ] Choose and explain indexes; read an `EXPLAIN` plan.
- [ ] Explain normalization vs denormalization with a trade-off example.
- [ ] Describe partitioning, replication, sharding and backups with PITR.
- [ ] Prepare a slow-query story and an incident story with root cause and prevention.
