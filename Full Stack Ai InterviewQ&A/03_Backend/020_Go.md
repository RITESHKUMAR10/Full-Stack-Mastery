# 🟢 Part 1: Fresher (0–1 year)

### Q1. What is Go?
A statically typed, compiled, garbage-collected language created at Google (Robert Griesemer, Rob Pike, Ken Thompson). It focuses on simplicity, fast compilation, built-in concurrency (goroutines and channels), a strong standard library, and easy deployment as a single static binary.
```go
package main

import "fmt"

func main() {
    fmt.Println("Hello, Ritesh Kumar")
}
```

### Q2. Why use Go? Typical use cases
Cloud and infrastructure (Docker, Kubernetes, Terraform are written in Go), network services and APIs, CLI tools, microservices, DevOps tooling, data pipelines. Strengths: simple syntax, fast builds, efficient concurrency, small static binaries, good performance, easy cross-compilation.

### Q3. How do you run, build and test Go code?
```bash
go run main.go          # compile and run
go build -o app ./cmd/app
go test ./...           # run all tests
go vet ./...            # static checks
go fmt ./...            # format (gofmt)
GOOS=linux GOARCH=arm64 go build   # cross-compile
```

### Q4. What are Go modules?
The dependency system. `go.mod` declares the module path, Go version and requirements; `go.sum` stores checksums. Commands: `go mod init example.com/app`, `go get pkg@version`, `go mod tidy`, `go mod vendor`.

### Q5. Basic types
`bool`, `string`, `int`, `int8..int64`, `uint..uint64`, `uintptr`, `float32/64`, `complex64/128`, `byte` (alias of `uint8`), `rune` (alias of `int32`, a Unicode code point). Zero values: `0`, `""`, `false`, `nil`.

### Q6. Variable declarations
```go
var a int = 10
var b = "text"          // type inferred
c := 3.14               // short declaration (only inside functions)
const Pi = 3.14159
var x, y = 1, 2
```
Unused variables and imports are compile errors.

### Q7. Zero values *(Must-know)*
Every variable has a usable default: numbers `0`, strings `""`, booleans `false`, pointers/slices/maps/channels/functions/interfaces `nil`. Good Go APIs make the zero value useful (for example `sync.Mutex`, `bytes.Buffer`).

### Q8. Functions and multiple return values
```go
func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("division by zero")
    }
    return a / b, nil
}
result, err := divide(10, 2)
```
Functions are first-class values; named returns are allowed (use sparingly); variadic: `func sum(nums ...int) int`.

### Q9. Control flow
Only `for` loops (no `while`), `if` with an optional init statement, `switch` without fallthrough by default.
```go
for i := 0; i < 3; i++ {}
for cond {}                 // while-style
for {}                      // infinite
for i := range 3 {}         // range over int (Go 1.22)
if v, ok := m["k"]; ok {}
switch x := f(); {
case x < 0:
default:
}
```

### Q10. Arrays vs slices *(Must-know)*
Arrays have a fixed length that is part of the type (`[3]int`) and are copied by value. Slices are dynamic views onto an underlying array: a struct of pointer, length, capacity.
```go
s := []int{1, 2, 3}
s = append(s, 4)
t := s[1:3]             // shares the same backing array
```

### Q11. `len` vs `cap`, and `append` behavior
`len` is the number of elements, `cap` the capacity of the backing array from the slice start. `append` reuses the array if there is capacity (shared mutation!); otherwise it allocates a bigger array (roughly doubling for small slices, growing more slowly for large ones) and copies.

### Q12. `make` vs `new`
`make(T, ...)` creates slices, maps and channels (initialized, ready to use). `new(T)` allocates zeroed memory and returns `*T`. Prefer composite literals (`&User{}`) over `new`.

### Q13. Maps
```go
m := map[string]int{"a": 1}
m["b"] = 2
v, ok := m["c"]         // ok is false if missing
delete(m, "a")
for k, v := range m {}  // random order
```
Writing to a nil map panics; reading from it is fine. Maps are not safe for concurrent use.

### Q14. Strings, bytes and runes
Strings are immutable byte sequences (usually UTF-8). Indexing gives bytes; `range` over a string yields runes.
```go
s := "héllo"
len(s)                  // 6 bytes
len([]rune(s))          // 5 runes
for i, r := range s {}  // i = byte index, r = rune
```
Use `strings.Builder` for concatenation in loops.

### Q15. Structs and methods
```go
type User struct {
    Name string
    Age  int
}
func (u User) Greeting() string   { return "Hi " + u.Name }   // value receiver
func (u *User) Birthday()         { u.Age++ }                 // pointer receiver
u := User{Name: "Ritesh Kumar", Age: 30}
```

### Q16. Value vs pointer receivers
Use a pointer receiver when the method mutates the receiver, the struct is large, or contains a mutex (must not be copied). Keep a type's methods consistent (all pointer receivers is a common rule).

### Q17. Pointers
`&x` takes an address, `*p` dereferences. Go has no pointer arithmetic. Pointers to local variables are safe because escape analysis moves them to the heap when needed.

### Q18. Interfaces *(Must-know)*
Interfaces are satisfied **implicitly** (no `implements`).
```go
type Shape interface { Area() float64 }
type Circle struct{ R float64 }
func (c Circle) Area() float64 { return 3.14159 * c.R * c.R }
var s Shape = Circle{R: 2}
```
"Accept interfaces, return structs." Keep interfaces small (`io.Reader` has one method).

### Q19. The empty interface and `any`
`any` is an alias for `interface{}`. Use type assertions or type switches to recover concrete types; prefer generics or specific interfaces over `any`.
```go
switch v := x.(type) {
case int:    fmt.Println("int", v)
case string: fmt.Println("string", v)
default:     fmt.Println("other")
}
```

### Q20. Error handling *(Must-know)*
Errors are values returned explicitly.
```go
f, err := os.Open("data.txt")
if err != nil {
    return fmt.Errorf("open data: %w", err)     // wrap with %w
}
defer f.Close()
```
Use `errors.Is(err, target)` and `errors.As(err, &target)` to inspect wrapped errors; define sentinel errors (`var ErrNotFound = errors.New("not found")`) and custom error types.

### Q21. `defer`
Schedules a call to run when the surrounding function returns (LIFO order). Arguments are evaluated immediately. Used for cleanup (`Close`, `Unlock`).
```go
mu.Lock()
defer mu.Unlock()
```

### Q22. `panic` and `recover`
`panic` stops normal flow (for unrecoverable bugs); deferred functions still run; `recover()` inside a deferred function can catch it. Use panics rarely (programmer errors, impossible states); return errors for expected failures. HTTP servers recover per-request panics.

### Q23. Goroutines *(Must-know)*
Lightweight concurrent functions managed by the Go runtime, starting with a small stack (a few KB) that grows dynamically.
```go
go doWork()
```
You can run hundreds of thousands. The program exits when `main` returns, even if goroutines are running.

### Q24. Channels *(Must-know)*
Typed conduits for communication between goroutines.
```go
ch := make(chan int)        // unbuffered: send blocks until a receiver is ready
buf := make(chan int, 10)   // buffered
go func() { ch <- 42 }()
v := <-ch
close(ch)                   // sender closes; receivers detect via v, ok := <-ch
```
"Do not communicate by sharing memory; share memory by communicating."

### Q25. `select`
Waits on multiple channel operations.
```go
select {
case msg := <-ch1:
case ch2 <- 5:
case <-time.After(time.Second):   // timeout
case <-ctx.Done():
default:                           // non-blocking
}
```

### Q26. `sync.WaitGroup`
```go
var wg sync.WaitGroup
for i := 0; i < 3; i++ {
    wg.Add(1)
    go func() { defer wg.Done(); work(i) }()
}
wg.Wait()
```
Call `Add` before starting the goroutine. (Go 1.25 adds `wg.Go(func())`: verify.)

### Q27. `sync.Mutex` and `RWMutex`
```go
type Counter struct { mu sync.Mutex; n int }
func (c *Counter) Inc() { c.mu.Lock(); defer c.mu.Unlock(); c.n++ }
```
Never copy a mutex after first use (`go vet` warns). `RWMutex` helps read-heavy workloads.

### Q28. Packages and visibility
Exported identifiers start with an uppercase letter. Package names are short lowercase. `internal/` directories restrict imports to the parent module tree. One package per directory; `main` package builds an executable.

### Q29. `init()` and `main()`
Each package can have `init()` functions run automatically at import time (after variable initialization); avoid heavy or side-effectful `init`. `main()` is the entry point.

### Q30. Constants and `iota`
```go
type Weekday int
const (
    Sunday Weekday = iota
    Monday
    Tuesday
)
```
Untyped constants have arbitrary precision until used.

### Q31. Struct tags and JSON
```go
type User struct {
    ID    int    `json:"id"`
    Name  string `json:"name"`
    Email string `json:"email,omitempty"`
    pass  string                       // unexported: ignored by JSON
}
b, _ := json.Marshal(u)
err := json.Unmarshal(b, &u)
```

### Q32. Basic HTTP server
```go
func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /hello/{name}", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintf(w, "Hello, %s", r.PathValue("name"))     // Go 1.22 routing patterns
    })
    log.Fatal(http.ListenAndServe(":8080", mux))
}
```

### Q33. Formatting verbs
`%v` default, `%+v` with field names, `%#v` Go syntax, `%T` type, `%d`, `%s`, `%q`, `%f`, `%x`, `%p`, `%w` (wrap error in `fmt.Errorf`).

### Q34. Common standard library packages
`fmt`, `strings`, `strconv`, `errors`, `io`, `os`, `bufio`, `bytes`, `time`, `sort`/`slices`/`maps`, `sync`, `context`, `net/http`, `encoding/json`, `log/slog`, `testing`, `regexp`, `path/filepath`, `flag`, `crypto/*`, `database/sql`.

### Q35. Testing basics
```go
func TestAdd(t *testing.T) {
    if got := Add(2, 3); got != 5 {
        t.Errorf("Add(2,3) = %d, want 5", got)
    }
}
```
Files end in `_test.go`; run `go test -v ./...`. Table-driven tests are idiomatic (see Part 2).

# 🔵 Part 2: Junior (1–3 years)

### Q36. Table-driven tests and subtests
```go
func TestAdd(t *testing.T) {
    tests := []struct {
        name       string
        a, b, want int
    }{
        {"positive", 2, 3, 5},
        {"zero", 0, 0, 0},
        {"negative", -1, -2, -3},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            t.Parallel()
            if got := Add(tt.a, tt.b); got != tt.want {
                t.Errorf("got %d, want %d", got, tt.want)
            }
        })
    }
}
```
Also: `go test -race`, `-cover`, `-bench`, fuzzing (`func FuzzX(f *testing.F)`), `testdata/`, `httptest`.

### Q37. Loop variable semantics (Go 1.22 change) *(Must-know)*
Before Go 1.22 the loop variable was shared across iterations, so closures/goroutines captured the same variable (classic bug). From Go 1.22 (when `go.mod` says `go 1.22` or later) each iteration has its own variable.
```go
for i := 0; i < 3; i++ {
    go func() { fmt.Println(i) }()   // Go 1.22+: prints 0,1,2 in some order; older: often 3,3,3
}
```
Know both behaviors because older code and `go.mod` versions matter.

### Q38. Slices of slices: aliasing pitfalls *(Must-know)*
```go
a := []int{1, 2, 3, 4}
b := a[:2]
b = append(b, 99)       // overwrites a[2] because capacity allows
```
Use the full slice expression `a[:2:2]` to cap capacity, or copy (`slices.Clone`, `copy`) to avoid aliasing. Subslices keep the whole backing array alive (memory retention).

### Q39. `copy`, `slices` and `maps` packages
```go
n := copy(dst, src)
slices.Sort(s); slices.Contains(s, 3); slices.Index(s, 3); slices.Reverse(s); slices.Max(s)
slices.SortFunc(users, func(a, b User) int { return cmp.Compare(a.Age, b.Age) })
maps.Keys(m)   // returns an iterator in 1.23+
```
Built-ins `min`, `max`, `clear` arrived in Go 1.21.

### Q40. Generics *(Must-know)*
```go
func Map[T, U any](in []T, f func(T) U) []U {
    out := make([]U, 0, len(in))
    for _, v := range in { out = append(out, f(v)) }
    return out
}
type Number interface{ ~int | ~int64 | ~float64 }
func Sum[T Number](xs []T) (s T) { for _, x := range xs { s += x }; return }
type Stack[T any] struct{ items []T }
```
Constraints: `any`, `comparable`, `cmp.Ordered`, custom interfaces with type sets. Use generics for data structures and algorithms, not as a replacement for interfaces.

### Q41. `context` package *(Must-know)*
Carries deadlines, cancellation signals and request-scoped values across API boundaries.
```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
```
Rules: pass `ctx` as the first parameter named `ctx`; never store it in structs (usually); always call `cancel`; use context values only for request-scoped metadata (trace IDs), not for optional parameters.

### Q42. Error wrapping and custom errors
```go
var ErrNotFound = errors.New("not found")
type ValidationError struct{ Field, Msg string }
func (e *ValidationError) Error() string { return e.Field + ": " + e.Msg }

err := fmt.Errorf("load user %d: %w", id, ErrNotFound)
if errors.Is(err, ErrNotFound) {}
var ve *ValidationError
if errors.As(err, &ve) {}
errors.Join(err1, err2)    // Go 1.20
```

### Q43. The typed-nil interface trap *(Must-know)*
```go
func f() error {
    var p *MyErr = nil
    return p            // non-nil error interface holding a nil pointer!
}
f() == nil              // false
```
An interface is `nil` only if both its type and value are nil. Return a literal `nil` for no error.

### Q44. Struct embedding (composition)
```go
type Animal struct{ Name string }
func (a Animal) Speak() string { return a.Name + " makes a sound" }
type Dog struct {
    Animal              // embedded: promotes fields and methods
    Breed string
}
d := Dog{Animal{"Rex"}, "Lab"}
d.Speak()
```
Go has no inheritance; embedding is composition with promotion. Embedded interfaces in structs are also used for decorators and partial mocks.

### Q45. JSON handling in depth
Custom marshaling via `MarshalJSON`/`UnmarshalJSON`, `json.Decoder` for streams, `DisallowUnknownFields()`, `json.RawMessage`, `omitempty` vs `omitzero` (Go 1.24), and pointers to distinguish missing from zero values.
```go
dec := json.NewDecoder(r.Body)
dec.DisallowUnknownFields()
if err := dec.Decode(&req); err != nil { /* 400 */ }
```
Limit body size with `http.MaxBytesReader`.

### Q46. HTTP handlers, middleware and the stdlib router
```go
type Middleware func(http.Handler) http.Handler
func logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)
        slog.Info("request", "method", r.Method, "path", r.URL.Path, "dur", time.Since(start))
    })
}
mux := http.NewServeMux()
mux.HandleFunc("POST /users", createUser)
mux.HandleFunc("GET /users/{id}", getUser)
http.ListenAndServe(":8080", logging(mux))
```
Popular routers: `chi`, `gorilla/mux`, `gin`, `echo`, `fiber`. The Go 1.22 stdlib mux (methods, wildcards) removed much of the need for third-party routers.

### Q47. Server timeouts *(Must-know)*
```go
srv := &http.Server{
    Addr: ":8080", Handler: mux,
    ReadHeaderTimeout: 5 * time.Second,
    ReadTimeout:       15 * time.Second,
    WriteTimeout:      30 * time.Second,
    IdleTimeout:       60 * time.Second,
}
```
`http.ListenAndServe` has no timeouts (vulnerable to slowloris). Also set client timeouts: `http.Client{Timeout: 10 * time.Second}`; never use `http.DefaultClient` for production calls without timeouts.

### Q48. Graceful shutdown
```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
go func() { if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) { log.Fatal(err) } }()
<-ctx.Done()
shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
_ = srv.Shutdown(shutdownCtx)
```

### Q49. Structured logging with `log/slog` (Go 1.21)
```go
logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo}))
logger.Info("user created", "id", 42, "name", "Ritesh Kumar")
logger.With("request_id", rid).Error("failed", "err", err)
```
Use `slog.Attr`, groups, and context-aware logging (`InfoContext`).

### Q50. `database/sql`
```go
db, err := sql.Open("pgx", dsn)       // does not connect yet
db.SetMaxOpenConns(25); db.SetMaxIdleConns(25); db.SetConnMaxLifetime(5 * time.Minute)
row := db.QueryRowContext(ctx, "SELECT name FROM users WHERE id = $1", id)
err = row.Scan(&name)                 // sql.ErrNoRows when absent
```
`*sql.DB` is a pool, safe for concurrent use. Always close `rows` (`defer rows.Close()`) and check `rows.Err()`. Use parameterized queries. Libraries: `pgx`, `sqlx`, `sqlc` (type-safe codegen), `GORM`, `ent`.

### Q51. Transactions
```go
tx, err := db.BeginTx(ctx, nil)
if err != nil { return err }
defer tx.Rollback()                   // no-op after Commit
if _, err := tx.ExecContext(ctx, q1, a); err != nil { return err }
return tx.Commit()
```

### Q52. `time` package essentials
`time.Now()`, `time.Since`, `time.Duration` arithmetic (`5*time.Second`), `time.Parse(layout, s)` with the reference time `Mon Jan 2 15:04:05 MST 2006`, monotonic clock handling, `time.NewTimer`/`Ticker` (stop them), and UTC for storage.

### Q53. Reading input and files
```go
f, _ := os.Open("big.txt"); defer f.Close()
sc := bufio.NewScanner(f)
sc.Buffer(make([]byte, 1024*1024), 1024*1024)    // raise the default 64KB token limit
for sc.Scan() { line := sc.Text() }
data, err := os.ReadFile("small.json")
```

### Q54. `io` interfaces
`io.Reader`, `io.Writer`, `io.Closer`, `io.ReadWriter`; helpers: `io.Copy`, `io.ReadAll`, `io.TeeReader`, `io.MultiWriter`, `io.Pipe`, `io.LimitReader`. Composition of small interfaces is a core Go design idea.

### Q55. Command-line flags and configuration
`flag` package for simple CLIs, `cobra`/`urfave/cli` for rich CLIs, environment variables (`os.Getenv`), `envconfig`/`viper` for configuration. Validate config at startup and fail fast.

### Q56. Build tags, `go:embed`, and `go generate`
```go
//go:embed templates/*
var templates embed.FS
//go:generate stringer -type=Weekday
```
Build tags (`//go:build linux`) select files per platform.

### Q57. Dependencies and versioning
Semantic import versioning (`/v2` suffix for major v2+), `go get -u`, `go mod tidy`, `replace` directives for local development, `go.work` workspaces for multi-module repos, and `GOFLAGS=-mod=vendor` for vendored builds. Use `govulncheck` for vulnerability scanning.

### Q58. Linting and tooling
`gofmt`/`goimports`, `go vet`, `staticcheck`, `golangci-lint`, `govulncheck`, `pprof`, `go tool trace`, `dlv` (Delve debugger), `go doc`.

### Q59. Project layout conventions
`cmd/<app>/main.go` entry points, `internal/` for private packages, `pkg/` (optional, debated) for public libraries, `api/` for OpenAPI/proto, `migrations/`. Prefer a flat, simple layout for small projects; do not over-structure.

### Q60. Unit testing HTTP handlers
```go
req := httptest.NewRequest(http.MethodGet, "/users/1", nil)
rr := httptest.NewRecorder()
handler.ServeHTTP(rr, req)
if rr.Code != http.StatusOK { t.Fatalf("status %d", rr.Code) }
```
For clients, `httptest.NewServer` provides a real in-process server.

### Q61. Mocking in Go
Define small interfaces at the consumer side; write fakes by hand or use `gomock`/`mockery`/`moq`. Prefer fakes and real dependencies (Testcontainers) over heavy mocking.

### Q62. Common anti-patterns
Ignoring errors (`_ =`), naked goroutines without lifecycle control, global mutable state, `panic` for control flow, huge interfaces, returning interfaces instead of concrete types, stuffing optional parameters into `context`, and premature use of `sync/atomic` or `unsafe`.

# 🟡 Part 3: Mid (3–5 years)

### Q63. The Go scheduler: G-M-P model *(Must-know)*
- **G**: goroutine. **M**: OS thread. **P**: logical processor (a scheduling context holding a local run queue).
- `GOMAXPROCS` sets the number of Ps (defaults to CPU cores; container awareness improved in newer versions: verify).
- Each P runs one G at a time on an M. When a goroutine blocks in a syscall, the runtime hands the P to another M. Idle Ps **steal work** from other Ps' queues. Since Go 1.14 scheduling is **asynchronously preemptive** (long-running loops are interrupted).

### Q64. Why are goroutines cheap?
Small initial stacks (about 2 KB, growable and shrinkable), user-space scheduling (no kernel context switch for goroutine switches), and cheap creation. Blocking on channels, mutexes or network I/O parks the goroutine without blocking an OS thread (netpoller).

### Q65. Channel patterns: worker pool *(Must-know)*
```go
func worker(id int, jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
    defer wg.Done()
    for j := range jobs { results <- process(j) }
}
jobs := make(chan int, 100)
results := make(chan int, 100)
var wg sync.WaitGroup
for w := 0; w < 8; w++ { wg.Add(1); go worker(w, jobs, results, &wg) }
go func() { for i := 0; i < 1000; i++ { jobs <- i }; close(jobs) }()
go func() { wg.Wait(); close(results) }()
for r := range results { _ = r }
```
Rules: only the **sender** closes a channel; sending on a closed channel panics; receiving from a closed channel returns zero values immediately.

### Q66. Fan-out/fan-in, pipelines, and cancellation
Compose stages connected by channels; each stage takes `ctx`, stops on `ctx.Done()`, and closes its output when done. Always make goroutines exit when the context is cancelled to avoid leaks.
```go
func gen(ctx context.Context, nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums {
            select { case out <- n: case <-ctx.Done(): return }
        }
    }()
    return out
}
```

### Q67. `errgroup` for structured concurrency
```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(8)
for _, u := range urls {
    g.Go(func() error { return fetch(ctx, u) })
}
if err := g.Wait(); err != nil { return err }
```
From `golang.org/x/sync/errgroup`. The first error cancels the context for siblings.

### Q68. Goroutine leaks *(Must-know)*
Causes: blocked sends/receives with no counterpart, missing `ctx.Done()` handling, forgotten `close`, unstopped tickers, orphaned goroutines after timeouts. Detect with `runtime.NumGoroutine()`, pprof goroutine profiles, and the `goleak` test helper. Fix with contexts, buffered channels for fire-and-forget results, and lifecycle ownership ("who stops this goroutine?").

### Q69. Data races and the race detector
A data race is concurrent access to the same memory where at least one is a write and there is no synchronization. Detect with `go test -race` / `go run -race` (use in CI). Fix with mutexes, channels, `atomic`, or by confining data to one goroutine.

### Q70. `sync` package tools
`Mutex`, `RWMutex`, `WaitGroup`, `Once` (`OnceFunc`, `OnceValue`), `Cond`, `Pool` (reuse temporary objects; may be cleared by GC), `Map` (for specific patterns: write-once-read-many, disjoint keys), `sync/atomic` (typed atomics like `atomic.Int64`).
```go
var once sync.Once
once.Do(initOnce)
var counter atomic.Int64
counter.Add(1)
```

### Q71. Mutex vs channel: which to use?
Use channels for passing ownership of data and coordinating goroutines (pipelines, signaling). Use mutexes to protect shared state (caches, counters). A mutex-guarded struct is often simpler and faster than channel-based "actors" for plain shared state.

### Q72. Deadlocks and "all goroutines are asleep"
The runtime detects total deadlock (`fatal error: all goroutines are asleep - deadlock!`) only when every goroutine is blocked. Partial deadlocks hang silently. Common causes: unbuffered channel send without receiver, lock ordering, forgetting `Unlock`, `WaitGroup` count mismatch.

### Q73. `sync.Pool` and allocation reduction
```go
var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}
buf := bufPool.Get().(*bytes.Buffer); buf.Reset()
defer bufPool.Put(buf)
```
Pools reduce GC pressure for hot paths; measure with benchmarks (`-benchmem`).

### Q74. Escape analysis and the stack vs heap
The compiler decides whether a variable can stay on the stack or must escape to the heap (returned pointers, captured by closures, stored in interfaces, too large). View with `go build -gcflags="-m"`. Fewer heap allocations mean less GC work.

### Q75. Garbage collector overview *(Must-know)*
Concurrent, tri-color mark-and-sweep, non-generational, non-moving collector with short stop-the-world phases. Tunables: `GOGC` (default 100: GC runs when heap grows 100% over live data), `GOMEMLIMIT` (soft memory limit, Go 1.19+), which is essential in containers. Reduce garbage first (fewer allocations, preallocation, pooling) before tuning knobs.

### Q78. Memory layout: struct padding
Fields are aligned; ordering large-to-small fields can reduce padding and memory. Check with `unsafe.Sizeof` or `fieldalignment` linter. Matters for huge slices of structs.

### Q79. String and byte conversions
`string(b)` and `[]byte(s)` copy. In hot paths use `strings.Builder`, `bytes.Buffer`, `unsafe.String`/`unsafe.Slice` carefully, and avoid repeated concatenation.

### Q80. Maps: iteration, concurrency, performance
Iteration order is intentionally randomized. Concurrent read+write panics with "concurrent map writes" (detected at runtime). Preallocate with `make(map[K]V, n)`. Go 1.24 introduced Swiss-table-based maps for better performance (implementation detail).

### Q81. Interfaces internals
An interface value is two words: type pointer (itab or type) and data pointer. Method calls through interfaces are dynamic dispatch; storing a non-pointer value may allocate. Comparing interfaces compares dynamic type and value (panics if the type is not comparable, such as slices or maps).

### Q82. Reflection and `unsafe`

### Q83. Code generation and tooling ecosystem

### Q84. gRPC and Protobuf in Go

### Q85. Configuration, secrets and 12-factor
Config from environment variables; secrets from a vault/KMS; one binary for all environments; logs to stdout; stateless processes; graceful shutdown; health endpoints.

### Q86. Dependency injection in Go
Prefer explicit constructor injection (`NewService(repo Repo, log *slog.Logger)`), wiring in `main`. Tools like `wire` (compile-time) or `fx` (runtime) exist but many teams avoid them for simplicity.

### Q87. Clean/hexagonal architecture in Go
Packages by domain (`user`, `order`) with interfaces defined where they are used (consumer side), a thin `transport` layer (HTTP/gRPC), `service` layer with business rules, and `storage` adapters. Avoid Java-style layering with interface-per-struct everywhere; interfaces appear when there are real alternatives or for testing seams.

### Q88. Rate limiting and backoff

### Q101. Concurrency design guidelines
Own your goroutines (clear start/stop), always pass `ctx`, bound everything (queues, workers, retries), prefer `errgroup` for fan-out, avoid sharing memory without synchronization, keep critical sections small, and write tests with `-race`. Document goroutine lifecycles.

### Q102. Mutex contention and atomics

### Q103. The Go memory model
Defines when a read in one goroutine is guaranteed to observe a write from another (happens-before): channel send happens-before the corresponding receive completes; `Unlock` happens-before the next `Lock`; `sync.Once` completion happens-before `Do` returns; `go` statement happens-before the goroutine starts. Without synchronization, behavior is undefined by the race rules.

### C1. HTTP JSON API with the standard library (CRUD, validation, timeouts)
```go

import (
    "context"
    "encoding/json"
    "errors"
    "log/slog"
    "net/http"
    "os"
    "os/signal"
    "strconv"
    "sync"
    "syscall"
    "time"
)

type User struct {
    ID   int    `json:"id"`
    Name string `json:"name"`
}

type store struct {
    mu     sync.RWMutex
    nextID int
    users  map[int]User
}

func newStore() *store { return &store{nextID: 1, users: map[int]User{}} }

func writeJSON(w http.ResponseWriter, status int, v any) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(status)
    _ = json.NewEncoder(w).Encode(v)
}

func (s *store) create(w http.ResponseWriter, r *http.Request) {
    r.Body = http.MaxBytesReader(w, r.Body, 1<<20)
    var in struct{ Name string `json:"name"` }
    dec := json.NewDecoder(r.Body)
    dec.DisallowUnknownFields()
    if err := dec.Decode(&in); err != nil || in.Name == "" {
        writeJSON(w, http.StatusBadRequest, map[string]string{"error": "invalid body"})
        return
    }
    s.mu.Lock()
    u := User{ID: s.nextID, Name: in.Name}
    s.users[u.ID] = u
    s.nextID++
    s.mu.Unlock()
    writeJSON(w, http.StatusCreated, u)
}

func (s *store) get(w http.ResponseWriter, r *http.Request) {
    id, err := strconv.Atoi(r.PathValue("id"))
    if err != nil {
        writeJSON(w, http.StatusBadRequest, map[string]string{"error": "bad id"})
        return
    }
    s.mu.RLock()
    u, ok := s.users[id]
    s.mu.RUnlock()
    if !ok {
        writeJSON(w, http.StatusNotFound, map[string]string{"error": "not found"})
        return
    }
    writeJSON(w, http.StatusOK, u)
}

func main() {
    st := newStore()
    mux := http.NewServeMux()
    mux.HandleFunc("POST /users", st.create)
    mux.HandleFunc("GET /users/{id}", st.get)
    mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, _ *http.Request) { w.WriteHeader(http.StatusOK) })

    srv := &http.Server{Addr: ":8080", Handler: mux, ReadHeaderTimeout: 5 * time.Second,
        ReadTimeout: 15 * time.Second, WriteTimeout: 30 * time.Second, IdleTimeout: 60 * time.Second}

    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()
    go func() {
        if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) {
            slog.Error("server failed", "err", err)
            os.Exit(1)
        }
    }()
    <-ctx.Done()
    sctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()
    _ = srv.Shutdown(sctx)
}
```

### C2. Worker pool with context cancellation
```go
func Process(ctx context.Context, items []int, workers int, fn func(context.Context, int) (int, error)) ([]int, error) {
    g, ctx := errgroup.WithContext(ctx)
    jobs := make(chan int)
    results := make([]int, len(items))
    g.Go(func() error {
        defer close(jobs)
        for i := range items {
            select {
            case jobs <- i:
            case <-ctx.Done():
                return ctx.Err()
            }
        }
        return nil
    })
    for w := 0; w < workers; w++ {
        g.Go(func() error {
            for i := range jobs {
                r, err := fn(ctx, items[i])
                if err != nil { return err }
                results[i] = r                   // each index written by one goroutine
            }
            return nil
        })
    }
    return results, g.Wait()
}
```

### C4. LRU cache (generic, goroutine-safe)
```go
type LRU[K comparable, V any] struct {
    mu  sync.Mutex
    cap int
    ll  *list.List
    m   map[K]*list.Element
}
type entry[K comparable, V any] struct{ k K; v V }

func NewLRU[K comparable, V any](cap int) *LRU[K, V] {
    return &LRU[K, V]{cap: cap, ll: list.New(), m: make(map[K]*list.Element)}
}
func (c *LRU[K, V]) Get(k K) (v V, ok bool) {
    c.mu.Lock(); defer c.mu.Unlock()
    if e, ok := c.m[k]; ok { c.ll.MoveToFront(e); return e.Value.(*entry[K, V]).v, true }
    return v, false
}
func (c *LRU[K, V]) Put(k K, v V) {
    c.mu.Lock(); defer c.mu.Unlock()
    if e, ok := c.m[k]; ok { e.Value.(*entry[K, V]).v = v; c.ll.MoveToFront(e); return }
    c.m[k] = c.ll.PushFront(&entry[K, V]{k, v})
    if c.ll.Len() > c.cap {
        last := c.ll.Back(); c.ll.Remove(last); delete(c.m, last.Value.(*entry[K, V]).k)
    }
}
```

### C5. Retry with exponential backoff and jitter

```go
func Retry(ctx context.Context, attempts int, base time.Duration, fn func(context.Context) error) error {
    var err error
    for i := 0; i < attempts; i++ {
        if err = fn(ctx); err == nil { return nil }
        d := base << i
        d = d/2 + time.Duration(rand.Int64N(int64(d)))
        select {
        case <-time.After(d):
        case <-ctx.Done():
            return ctx.Err()
        }
    }
    return fmt.Errorf("after %d attempts: %w", attempts, err)
}
```

```go
func TwoSum(nums []int, target int) (int, int, bool) {
    seen := map[int]int{}
    for i, n := range nums {
        if j, ok := seen[target-n]; ok { return j, i, true }
        seen[n] = i
    }

    lo, hi := 0, len(a)-1

        mid := lo + (hi-lo)/2

        case a[mid] < x:  lo = mid + 1
```

# 🐞 Part 7: Debugging Scenarios

### D1. `fatal error: all goroutines are asleep - deadlock!`
Every goroutine is blocked. Check unbuffered channel sends without receivers, `WaitGroup.Wait()` with missing `Done`, missing `close` in `range` loops, or mutex lock ordering. Read the goroutine dump printed with the error.

### D2. `panic: assignment to entry in nil map`
Map not initialized. Use `make(map[K]V)` or a literal; zero-value structs containing maps need initialization in constructors.

### D3. `panic: send on closed channel` / `close of closed channel`
Multiple closers or sender/receiver confusion. Only one owner (the sender) closes; use `sync.Once` or a done channel for multiple producers.

### D4. `fatal error: concurrent map writes` / `concurrent map read and map write`
Unsynchronized map access. Protect with `sync.RWMutex`, use `sync.Map` for suitable patterns, or confine the map to a single goroutine. Run `go test -race` to find all sites.

### D5. Goroutine count keeps growing
Leak: goroutines blocked forever on channels or I/O without timeouts. Take a goroutine profile (`/debug/pprof/goroutine?debug=2`), find common stacks, and add context cancellation/timeouts and proper channel closing.

### D6. Memory keeps growing
Heap profile comparison: look for growing caches, retained subslices of large arrays, unbounded channels/queues, leaked goroutines holding references, `time.Ticker` not stopped, and global maps. Fix and add limits.

### D7. High CPU / GC overhead
CPU profile shows `runtime.mallocgc`/`gcBgMarkWorker`: reduce allocations (preallocate, pool, avoid `fmt` in hot loops), check JSON reflection costs, and tune `GOGC`/`GOMEMLIMIT` after reducing garbage.

### D8. Slow HTTP requests / hung connections
Missing client timeouts, no context deadlines, response body not closed (connection leak), or exhausted connections per host. Always `defer res.Body.Close()` and drain if reusing connections; configure `http.Transport` (`MaxIdleConnsPerHost`, timeouts).

### D9. `too many open files`
Leaked file descriptors (unclosed files/bodies/rows) or high concurrency. Close resources with `defer`, limit concurrency, and raise `ulimit -n` if appropriate.

### D10. Loop variable bug (older Go)
Goroutines/closures all see the last value. Upgrade `go.mod` to Go 1.22+ semantics or shadow the variable (`i := i`).

### D11. Unexpected `nil` error behavior (typed nil)
A function returns a nil pointer as an `error` interface, making `err != nil` true. Return explicit `nil`; avoid returning concrete error pointer types from functions typed as `error`.

### D12. `sql: Scan error` / `sql: no rows in result set`
Handle `sql.ErrNoRows`; use `sql.NullString`/pointers for nullable columns; check column count and types; always check `rows.Err()`.

### D13. Database connection pool exhaustion
Unclosed `rows`, long transactions, or too many concurrent queries. Close rows, defer rollbacks, set `SetMaxOpenConns`, and add timeouts via contexts.

### D14. JSON decoding surprises
Unexported fields ignored, case-insensitive matching, numbers decoded as `float64` into `any`, missing vs zero values (use pointers), unknown fields silently ignored unless `DisallowUnknownFields`. Use `json.Number` or typed structs.

### D15. Time-related bugs
Local vs UTC, monotonic clock comparisons, wrong layout strings, timers not stopped (`Ticker.Stop`). Use UTC, `time.Duration` arithmetic, and inject a clock for tests.

### D16. Build errors: import cycles, unused imports/variables
Restructure packages (move shared types to a lower-level package, use interfaces at boundaries). Run `goimports` to fix unused imports.

### D17. Module and dependency problems
`go: updates to go.mod needed` or checksum mismatches: run `go mod tidy`, check `GOFLAGS`, `GOPROXY`/`GONOSUMDB` settings for private modules, and avoid committing local `replace` directives.

### D18. Data race detected (`WARNING: DATA RACE`)
The report shows both conflicting accesses and goroutine creation stacks. Add synchronization or restructure ownership. Never ignore race reports.

### D19. Process killed in container (OOMKilled)
Memory limit exceeded. Set `GOMEMLIMIT` below the limit, reduce allocations, bound caches/queues, and check for goroutine leaks. Go may not return memory to the OS immediately (scavenger behavior).

### D20. Debugging method (say this in interviews)
Reproduce → add observability (logs/metrics) → use the right profile (CPU, heap, goroutine, mutex/block, trace) → form a hypothesis → fix → write a regression test (with `-race`) → add monitoring.

# 🧩 Part 8: Tricky Questions

### T1. Is Go pass-by-value or pass-by-reference?
Always pass-by-value. Slices, maps, channels, functions and pointers are small descriptors/references copied by value; the copy points to the same underlying data. So a function can mutate a slice's elements or a map, but appending inside a function may not be visible to the caller (the slice header is a copy).

### T2. Why can `append` inside a function not update the caller's slice?
`append` may return a new slice header (length changed, maybe a new array). The caller's header is unchanged unless you return the slice or pass a pointer.
```go
func add(s []int) { s = append(s, 1) }       // caller does not see the new length
func add2(s []int) []int { return append(s, 1) }
```

### T3. Two slices share memory unexpectedly
Subslices share the backing array until `append` exceeds the capacity. Use `slices.Clone`, `copy`, or `s[a:b:b]` to avoid surprises.

### T4. Why is `nil` slice different from an empty slice?
`var s []int` is `nil` (len 0, cap 0, no array); `[]int{}` is non-nil and empty. Both work with `len`, `append`, `range`. JSON encodes nil slices as `null`, empty slices as `[]`.

### T5. Why do map iterations give different orders?
The runtime randomizes iteration order intentionally so code does not depend on it. Sort keys if you need order.

### T6. Can you take the address of a map element?
No (`&m[k]` is illegal) because elements can move on growth. Store pointers in the map or copy, modify, and write back. Also `m[k].field = v` is illegal for struct values.

### T7. Comparing interfaces holding uncomparable types
`==` on interfaces whose dynamic type is a slice, map or function panics at runtime. Use `reflect.DeepEqual` or `slices.Equal`.

### T8. `defer` evaluation order
Deferred call arguments are evaluated at the `defer` statement; the call runs later in LIFO order.
```go
for i := 0; i < 3; i++ { defer fmt.Print(i) }     // prints 210
```

### T9. `defer` in a loop
Deferred calls accumulate until the function returns (file descriptors may pile up). Wrap the body in a function or close explicitly.

### T10. `defer` modifying named results
```go
func f() (n int) { defer func() { n *= 2 }(); return 21 }    // returns 42
```
Deferred closures can modify named return values.

### T11. `recover` only works inside a deferred function
Calling `recover()` anywhere else returns `nil`. It also doesn't catch panics from other goroutines.

### T12. Panics in goroutines crash the whole program
An unrecovered panic in any goroutine terminates the process. Recover at goroutine boundaries (worker wrappers, HTTP handlers).

### T13. Unbuffered vs buffered channel semantics
Unbuffered send blocks until a receiver is ready (synchronization point). Buffered send blocks only when full. Buffers are not a fix for deadlocks, only for decoupling bursts.

### T14. Receiving from a nil channel
Blocks forever (both send and receive). Used deliberately in `select` to disable a case.

### T15. `select` with multiple ready cases
Chooses one pseudo-randomly. Priority requires nested selects or explicit checks.

### T16. `for range ch` ends when?
When the channel is closed and drained. Forgetting to close leads to goroutines blocked forever.

### T17. Does `time.After` leak in loops?
Each call allocates a timer that is not garbage collected until it fires (older versions). Since Go 1.23 unreferenced timers are collectable, but prefer `time.NewTimer` + `Stop`/`Reset` in hot loops.

### T18. `sync.WaitGroup` copy bug
Passing a `WaitGroup` by value copies it, so `Done` affects a copy. Pass a pointer (or capture by closure).

### T19. Struct containing a mutex copied by value
`go vet` flags it (`copylocks`). Copying breaks locking semantics. Use pointer receivers and avoid copying.

### T20. Method value vs method expression binding
`f := obj.Method` binds the receiver at that time (copying a value receiver). Later changes to `obj` do not affect `f` for value receivers.

### T21. Shadowed variables with `:=`
```go
var err error
if x { v, err := f(); _ = v } // new err inside; outer err unchanged
```
Common cause of ignored errors; enable `govet shadow` or linters.

### T22. String iteration gotcha
`len("héllo")` is bytes; ranging yields runes; indexing yields bytes. Slicing in the middle of a multi-byte character produces invalid UTF-8.

### T23. Integer overflow and conversion
Integer overflow wraps silently. Converting `float64` to `int` truncates; out-of-range conversions are implementation-defined. Use `math.MaxInt` checks, `strconv.ParseInt` with bit sizes.

### T24. `init()` order and side effects
Package-level variables initialize in dependency order, then `init()` functions run in file name order presented to the compiler. Avoid logic in `init`; it complicates testing.

### T25. Unused variables are errors but unused function params aren't
Name unused parameters `_` when appropriate.

### T26. `copy` returns min(len(dst), len(src))
`copy(dst, src)` into an empty slice copies nothing. Allocate with `make([]T, len(src))` first.

### T27. Why does `for i, v := range slice` give copies?
`v` is a copy of the element. Modifying `v` does not change the slice; index (`slice[i]`) or use pointers to elements.

### T28. Zero-size types
`struct{}` occupies zero bytes; used for sets (`map[T]struct{}`) and signals (`chan struct{}`).

# 🔬 Part 12: Go Runtime Internals

### I1. Compilation and linking
`go build` compiles packages to object files (SSA-based compiler), links into a single statically linked binary (including the runtime) by default. Build is fast due to dependency analysis and no header files. Cgo or the `net` package with the system resolver can introduce dynamic linking unless disabled (`CGO_ENABLED=0`, `-tags netgo`).

### I2. The scheduler (G-M-P) in detail
Each P has a local run queue (256 goroutines); there is a global queue. `schedule()` picks from the local queue, occasionally the global queue and the network poller; if empty, it steals half from another P. Blocking syscalls detach the M from the P (via sysmon handoff) so other goroutines continue. `sysmon` is a background monitor thread that handles retaking Ps and preemption.

### I3. Preemption
Cooperative preemption at function prologues (stack checks) plus asynchronous preemption using signals (since Go 1.14), so tight loops without function calls can be preempted.

### I4. The network poller
Network I/O uses non-blocking sockets with epoll/kqueue/IOCP. A goroutine blocked on a read is parked, and the poller wakes it when the descriptor is ready. This is why thousands of connections need few threads.

### I5. Stack management
Goroutine stacks start small and grow by allocating a larger contiguous stack and copying (contiguous stacks since Go 1.4). The GC can shrink stacks. Pointers into stacks are adjusted during copying (which is why you cannot store raw stack addresses safely).

### I6. Memory allocator
TCMalloc-inspired: per-P caches (`mcache`) of size-classed spans (`mspan`), central lists (`mcentral`), and the page heap (`mheap`). Small objects (≤32 KB) use size classes; large objects allocate directly. Pointer-free (noscan) spans are not scanned by the GC.

### I7. Garbage collector phases
Sweep termination (STW) → concurrent mark (with write barriers, using assists from allocating goroutines) → mark termination (STW) → concurrent sweep. Pacing aims to finish marking before the heap reaches the GC target (based on `GOGC` and `GOMEMLIMIT`). STW pauses are typically sub-millisecond.

### I8. Escape analysis
The compiler determines whether values may outlive their stack frame. Escapes to heap if address returned, captured by a closure that escapes, stored in an interface or global, sent over a channel, or too large. Inspect with `-gcflags='-m -m'`.

### I9. Interface and itab
Non-empty interfaces store an `itab` pointer (type + method table) and a data pointer; empty interfaces store a type pointer and data pointer. Method calls load the function from the itab. The compiler can devirtualize when the concrete type is known (and PGO can help).

### I10. Maps internals
Traditionally buckets of 8 entries with tophash bytes and overflow chains, incremental growth; Go 1.24 switched to Swiss tables (open addressing with groups and SIMD-friendly control bytes). Randomized iteration start; map access is not atomic.

### I11. Channels internals
A channel (`hchan`) holds a circular buffer, queues of waiting senders/receivers (`sudog`), and a lock. Direct handoff happens when a receiver is waiting. Channels are not free: for tiny critical sections a mutex or atomic is faster.

### I12. Generics implementation
GC-shape stenciling with dictionaries: instantiations are grouped by underlying shape (all pointers share one shape), reducing code bloat while keeping reasonable performance. Method calls on type parameters may go through dictionaries.

### I13. Modules and the toolchain
Minimal version selection (MVS) picks the minimum version satisfying all requirements (deterministic, no lockfile solver). The `toolchain` directive lets `go` fetch the required Go version automatically.

# ⚠️ Part 16: Common Mistakes

> Each mistake has four parts: ❌ wrong code, 🤔 why it is a problem, ✅ correct code, 💬 what to say in an interview.

### Mistake 1: Ignoring errors
❌
```go
data, _ := os.ReadFile("config.json")
json.Unmarshal(data, &cfg)
```
🤔 Failures pass silently and the program continues with bad state.
✅
```go
data, err := os.ReadFile("config.json")
if err != nil { return fmt.Errorf("read config: %w", err) }
if err := json.Unmarshal(data, &cfg); err != nil { return fmt.Errorf("parse config: %w", err) }
```
💬 "Errors are values: I handle or wrap every one with context."

### Mistake 2: Goroutine leaks
❌
```go
func fetch() string {
    ch := make(chan string)
    go func() { ch <- slowCall() }()
    select {
    case r := <-ch: return r
    case <-time.After(time.Second): return "timeout"
    }
}
```
🤔 After the timeout the goroutine blocks forever on the unbuffered send.
✅
```go
ch := make(chan string, 1)      // buffered so the sender can finish
```
💬 "Every goroutine needs a clear way to exit: buffering, contexts, or closing."

### Mistake 3: No timeouts on HTTP clients and servers
❌
```go
resp, err := http.Get(url)
http.ListenAndServe(":8080", mux)
```
🤔 Calls hang indefinitely; the server is exposed to slow clients.
✅
```go
client := &http.Client{Timeout: 10 * time.Second}
srv := &http.Server{Addr: ":8080", Handler: mux, ReadHeaderTimeout: 5 * time.Second, IdleTimeout: 60 * time.Second}
```
💬 "I never use default clients or servers in production."

### Mistake 4: Forgetting to close response bodies and rows
❌
```go
resp, _ := client.Do(req)
body, _ := io.ReadAll(resp.Body)
```
🤔 Connections and file descriptors leak.
✅
```go
resp, err := client.Do(req)
if err != nil { return err }
defer resp.Body.Close()
```
💬 "Always `defer Close()` right after a successful open; also check `rows.Err()`."

### Mistake 5: Data races on shared state
❌
```go
var count int
for i := 0; i < 100; i++ { go func() { count++ }() }
```
🤔 `count++` is not atomic.
✅
```go
var count atomic.Int64
for i := 0; i < 100; i++ { go func() { count.Add(1) }() }
```
💬 "I run tests with `-race` and protect shared state with mutexes or atomics."

### Mistake 6: Misusing `defer` in loops
❌
```go
for _, f := range files { fh, _ := os.Open(f); defer fh.Close() }
```
🤔 Files stay open until the function returns.
✅
```go
for _, f := range files { func() { fh, err := os.Open(f); if err != nil { return }; defer fh.Close(); process(fh) }() }
```
💬 "Defer runs at function exit, so I scope it to a helper function in loops."

### Mistake 7: Using `panic` for normal errors
❌
```go
if err != nil { panic(err) }
```
🤔 Crashes the program; callers cannot handle it.
✅
```go
if err != nil { return nil, err }
```
💬 "Panics are for programmer errors; expected failures return errors."

### Mistake 8: Aliased slices
❌
```go
func first2(s []int) []int { return s[:2] }       // shares memory with a huge array
```
🤔 Keeps the whole array alive and allows accidental mutation.
✅
```go
func first2(s []int) []int { return slices.Clone(s[:2]) }
```
💬 "I copy when returning subslices that outlive the source."

### Mistake 9: Overusing interfaces and abstractions
❌
```go
type UserServiceInterface interface { /* 20 methods */ }
```
🤔 Adds indirection without value and makes changes painful.
✅
```go
type userStore interface { Get(ctx context.Context, id int) (User, error) }   // small, defined by the consumer
```
💬 "Accept small interfaces, return concrete types."

### Mistake 10: Not using `context` for cancellation
❌
```go
func process(items []Item) { for _, it := range items { slowCall(it) } }
```
🤔 Work continues after the caller gives up.
✅
```go
func process(ctx context.Context, items []Item) error {
    for _, it := range items { if err := slowCall(ctx, it); err != nil { return err } }
    return nil
}
```
💬 "Context is the first parameter of anything that can block or take time."

### Mistake 11: Global mutable state
❌
```go
var db *sql.DB
func init() { db, _ = sql.Open("pgx", os.Getenv("DSN")) }
```
🤔 Hard to test, hidden dependencies, hidden errors.
✅
```go
type Server struct{ db *sql.DB }
func NewServer(db *sql.DB) *Server { return &Server{db: db} }
```
💬 "Explicit dependency injection through constructors."

### Mistake 12: Unbounded concurrency
❌
```go
for _, u := range urls { go fetch(u) }          // 100,000 goroutines hitting one host
```
🤔 Overloads the network and the remote service.
✅
```go
g, ctx := errgroup.WithContext(ctx); g.SetLimit(10)
```
💬 "I always bound concurrency."

### Mistake 13: Copying locks or using `WaitGroup` by value
❌
```go
func run(wg sync.WaitGroup) { defer wg.Done() }
```
🤔 `wg` is copied; the original never sees `Done`; deadlock.
✅
```go
func run(wg *sync.WaitGroup) { defer wg.Done() }
```
💬 "Sync primitives must not be copied; `go vet` catches this."

### Mistake 14: Comparing errors with `==` instead of `errors.Is`
❌
```go
if err == ErrNotFound { }
```
🤔 Fails once the error is wrapped.
✅
```go
if errors.Is(err, ErrNotFound) { }
```
💬 "Wrapped errors need `errors.Is` and `errors.As`."

### Mistake 15: Optimizing without measuring
❌
```go
// replaced fmt.Sprintf everywhere "for speed"
```
🤔 Wasted effort and less readable code.
✅
```go
// benchmark with -benchmem, profile with pprof, fix the top item, re-measure
```
💬 "Profile first, optimize second."

# 🧾 Part 18: Cheat Sheet & Last-Minute Revision

### 1. The 30-second explanation
Go is a simple, statically typed, compiled language with a garbage collector and first-class concurrency: goroutines scheduled by a G-M-P runtime scheduler, channels for communication, and `context` for cancellation. It ships a rich standard library, fast builds, and static binaries, which makes it a favorite for cloud services and infrastructure.

### 2. Core mental models
- Zero values are useful; make them so.
- Slices are views (pointer, len, cap); appends may or may not reallocate.
- Interfaces are satisfied implicitly; keep them small.
- Errors are values; wrap with `%w`.
- Every goroutine needs an exit path; every call that can block needs a context.

### 3. Concurrency checklist
- [ ] Who owns and stops each goroutine?
- [ ] Context passed and honored?
- [ ] Concurrency bounded (workers, semaphores, `SetLimit`)?
- [ ] Channels closed by the sender only?
- [ ] Shared state protected; `-race` clean?
- [ ] Timeouts on I/O?

### 4. Production checklist
- [ ] Supported Go version and pinned toolchain
- [ ] Server and client timeouts configured
- [ ] Graceful shutdown with `signal.NotifyContext` and `Shutdown`
- [ ] Structured logging (`slog`), metrics, traces, protected pprof
- [ ] `GOMEMLIMIT` set in containers; static binary in a minimal image
- [ ] `golangci-lint`, `go vet`, `govulncheck`, `go test -race` in CI
- [ ] Config from environment; secrets from a vault
- [ ] Health and readiness endpoints
- [ ] Backoff + jitter retries; circuit breakers on dependencies
- [ ] Benchmarks and profiles for critical paths

### 5. Debug toolbox
| Symptom | Tool |
|---|---|
| High CPU | CPU pprof / flame graph |
| Memory growth | Heap pprof (compare snapshots) |
| Goroutine growth | Goroutine pprof, `goleak` |
| Latency spikes | `runtime/trace`, `GODEBUG=gctrace=1` |
| Lock contention | Mutex/block profiles |
| Races | `go test -race` |

### 6. Top 20 one-liners to memorize
1. Errors are values.
2. Wrap errors with `%w`; check with `errors.Is/As`.
3. Zero values should be useful.
4. Only the sender closes a channel.
5. A nil map read is fine; a nil map write panics.
6. Slices share memory until reallocation.
7. `defer` runs at function exit (LIFO).
8. Arguments to `defer` are evaluated immediately.
9. `context` first, always.
10. Bound concurrency.
11. Set HTTP client and server timeouts.
12. Typed nil in an interface is not nil.
13. Run tests with `-race`.
14. Profile before optimizing.
15. Accept interfaces, return structs.
16. Prefer composition via embedding.
17. Keep interfaces small and consumer-defined.
18. `GOMEMLIMIT` for containers.
19. Don't copy mutexes or WaitGroups.
20. Simple beats clever.

### 7. The 60-second answer: "Why Go?"
"Go gives me simple, readable code, very fast builds and deployment as a single static binary, and excellent built-in concurrency with goroutines and contexts. It's a great fit for network services and infrastructure where predictable performance and low operational overhead matter. I rely on the standard library, strict timeouts and contexts, and tools like pprof and the race detector to keep services reliable."

### 8. Final revision order
Types, slices and maps → functions, errors and `defer` → interfaces, embedding and generics → goroutines, channels and `context` → sync primitives and memory model → HTTP, JSON and database/sql → testing, profiling and the runtime (scheduler, GC) → production practice and debugging stories.
